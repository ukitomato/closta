# Feature Specification: セッションの再開 (resume) (X-9)

**Feature Branch**: `021-session-resume`

**Created**: 2026-10-21

**Status**: frontmatter の `status:` を正とする

**Input**: roadmap M3 の順 22 の X-9 の行 (範囲の正本)。2026-10-19 に X-6 から切り出した (AD-041 (h) が X-6 に指名した「fork / resume / rename / tag / delete」のうち resume と、X-5 FR-013 が自動で行わないとした失敗したセッションの再開)。domain は roadmap の行のとおり `session`。

## Summary

終わった会話の続きを Closta から話せるようにする。今は過去のセッションは読むだけで (composer は閉じている)、終了済み・失敗した稼働中の行は閉じるしかない。会話を続けるには新しいセッションを起動し、文脈を一から渡し直すことになる。

- **過去のセッションの再開**: サイドバーの過去の区画の行から、その会話を Agent SDK の `resume` で再開する
- **止まった・失敗したセッションの再開**: 稼働中の区画の終了済みの行と失敗した行から、同じ会話を利用者の操作で再開する (自動では再開しない。X-5 FR-013 のまま)
- **軸の引き継ぎ**: フォルダ / ランタイム / Provider は元の会話から引き継いで変えられない。モデル / effort / 権限モードは再開のときに選び直せる (session charter Journey 4 の手順 1〜2)
- **続きの表示**: 再開したセッションの中央に、それまでの会話を読み取り専用で出し、その下に新しいやり取りを流す

Closta で Closta を開発できるようにする 2 本の 2 本目 (1 本目は X-8 の Win32 の直接起動)。

## 本 feature の位置づけ

- **session の feature で、agents の query の options と main の registry に触れる。** `resume` は会話の続きを読み込むだけで、権限面・tool の集合・env を変えない (escalation-neutral)。権限モードは安全 3 値のまま (AD-041 (a))。この前提は、再開の起動の最初の `system/init` が報告する権限モードを検査し、安全 3 値の外なら失敗にして止めることで裏付ける (FR-017)。会話の id は main と agents の境界で UUID の形を検査する
- **Principle X のまま。** 会話の正本は Claude Code の transcript (`<config-dir>/projects/<encoded-cwd>/<uuid>.jsonl`) で、Closta は会話の id を永続化しない (稼働中の行の id はメモリの registry にだけ持ち、過去の行の id は列挙の結果から取る)
- **引き継ぐ軸を変えない理由**: `claude` は再開する会話を「作業フォルダ (cwd) × config ディレクトリ (Provider) × ランタイム (どの `claude` とファイルシステムか)」の組で探す。どれかを変えると同じ会話が見つからないか、別の会話になる。軸を変えて続けるのは分岐 (`forkSession`) で X-6 に残す
- **起動ゲートと上限は今のまま。** 再開は新しい起動の 1 本として起動ゲート・同時実行数の上限 (10)・Win32 / WSL の起動の値の組み立てを通る

## Clarifications

### Session 2026-10-21 (夜間の規則で推奨案を採用)

- **U-1** Q: 稼働中の行の会話の id をどう知るか → 検討した案: (a) SDK の `system/init` の `session_id` を session thread で受け、形を検査して main の registry に運ぶ (b) 起動のときに Closta の `sessionId` を SDK の `sessionId` の option で渡し、会話の id と同じにする (c) 稼働中の行からは再開させず、過去の区画の行からだけ再開する → **採った案: (a)**。(b) は再開した会話の id が元の行の `sessionId` と同じになり、稼働中の行の鍵が衝突する。(c) は失敗した行の再開 (roadmap の義務) を満たせない。採用 (2026-10-21 夜間の規則で推奨案を採用)
- **U-2** Q: モデル / effort / 権限モードをどこで選び直すか → 検討した案: (a) 起動ダイアログを再開の形で開く (b) 行の「再開」で元の設定のまま即座に再開し、変えたいときだけダイアログ (c) 再開専用の小さなダイアログ → **採った案: (a)**。今の依存解決 (Provider → モデル → effort) とプリセットの規則を再利用でき、Journey 4 の「選び直せる」を 1 か所で満たす。採用 (2026-10-21 夜間の規則で推奨案を採用)
- **U-3** Q: 過去の行の軸をどう解くか → 検討した案: (a) 列挙対象 (config ディレクトリ × 所在) と行の cwd から、登録フォルダ・ランタイム・Provider を決め、決まらなければ理由つきで拒否 (b) 決まらない軸を利用者に選ばせる (c) 登録フォルダに対応づく行だけに「再開」を出す → **採った案: (a)**。(b) は別の config ディレクトリ・cwd で会話が見つからない組み合わせを作れる。(c) は理由が分からない。未登録の行は今の R-2 の登録の導線で直せる。採用 (2026-10-21 夜間の規則で推奨案を採用)
- **U-4** Q: 稼働中の行から再開したとき元の行をどうするか → 検討した案: (a) 新しい行の起動を受け付けたら元の行を閉じ、新しい行を選ぶ (b) 元の行を残し利用者が閉じる (今の FR-011 の閉じる) → **採った案: (a)**。同じ会話の行が 2 つ並ぶと、どちらが続きか分からない。起動が拒否されたときは元の行を残す。採用 (2026-10-21 夜間の規則で推奨案を採用)
- **U-5** Q: 同じ会話を同時に 2 本再開しようとしたら → 検討した案: (a) 拒否してその行を選ぶ (b) 警告を出して起動を許す (同じフォルダの並行起動と同じ扱い) → **採った案: (a)**。同じ transcript に 2 つの `claude` が書くと記録が混ざる。Closta の外 (CLI) で同じ会話が動いているかは見分けられない (Edge Cases)。採用 (2026-10-21 夜間の規則で推奨案を採用)
- **U-6** Q: 会話の id を持たない失敗の行 (`claude-not-found`・`launch-failed`・最初の init の前の `process-crashed` など) の「再開」 → 検討した案: (a) 同じ起動設定を初期値にした新規起動のダイアログを開く (b) 再開の操作を出さない → **採った案: (a)**。利用者から見ると同じ「やり直す」で、ダイアログで原因 (claude の場所・Provider) を直してから起動できる。採用 (2026-10-21 夜間の規則で推奨案を採用)
- **U-7** Q: それまでの会話を再開したセッションで出すか → 検討した案: (a) 再開のときに R-3 の読み取りの経路で 1 回読み、中央の先頭に読み取り専用で出す (b) 新しいやり取りだけを出し、過去ログへの導線を付ける → **採った案: (a)**。続きを話すには直前の文脈が見えている必要がある。SDK は `resume` で過去のメッセージを stream に流さない (対応表の `SDKUserMessageReplay` は表示不要のまま)。採用 (2026-10-21 夜間の規則で推奨案を採用)
- **U-8** Q: 中断しただけの行 (`claude` が動いている) を再開の対象にするか → 検討した案: (a) 対象にしない (b) `claude` を止めて再開し直す → **採った案: (a)**。次のプロンプトを送れば続く。動いているセッションのモデルなどを変えるのは X-6 の範囲。採用 (2026-10-21 夜間の規則で推奨案を採用)
- Q: 行の操作の文言 → A: 「再開」。会話の id が無い失敗の行は「やり直す」。再開の形のダイアログの見出しは「セッションを再開」、起動のボタンは「再開する」 [ASSUMED: UI ラベル・ボタン文言]
- Q: 再開の形のダイアログの選び直せる軸の初期値 → A: 稼働中の行は元の起動設定の値、過去の行はダイアログの今の既定 (依存解決の結果) [ASSUMED: デフォルト表示状態]
- Q: 再開を拒否したときの文言 → A: 未登録フォルダ「この会話の作業フォルダは登録されていません。フォルダを登録してから再開してください」、Provider が無い「この会話の config ディレクトリに対応する Provider がありません。Provider を登録してから再開してください」、同じ会話が動いている「この会話はすでに実行中です」 [ASSUMED: エラーメッセージ文言]
- Q: それまでの会話と新しいやり取りの境目 → A: 「ここから再開」の区切りの行を 1 つ出す [ASSUMED: UI ラベル・デフォルト表示状態]

## User Scenarios & Testing

### User Story 1 - 過去のセッションの続きを話せる (Priority: P1)

利用者はサイドバーの過去の区画で昨日の会話を選び、「再開」から続きを話す。`claude` はそれまでの文脈を覚えている。

**Why this priority**: 本題。今は過去の会話を読めても続けられず、新しいセッションに文脈を渡し直している。

**Independent Test**: WSL と Win32 のそれぞれで 1 ターン話した会話を終了し、過去の区画から再開して、前のターンの内容に触れる問いに `claude` が答えられることを確かめる。

**Acceptance Scenarios**:

1. **Given** 登録フォルダに対応づき、対応する Provider がある過去の行、**When** 行を選ぶ、**Then** 「再開」の操作が出る
2. **Given** 上の行、**When** 「再開」から再開する、**Then** 新しい稼働中の行が起き、中央にそれまでの会話と、その下に composer が出る
3. **Given** 再開したセッション、**When** 前のターンの内容に触れる問いを送る、**Then** `claude` は同じ会話の続きとして答え、記録は元の transcript (同じ会話の id) に追記される
4. **Given** 登録フォルダに対応づかない過去の行、**When** 行を選ぶ、**Then** 「再開」は理由つきで押せず、R-2 の登録の導線が出る
5. **Given** 対応する Provider が無い過去の行 (列挙対象の config ディレクトリが登録の無いもの)、**When** 行を選ぶ、**Then** 「再開」は理由と直し方つきで押せない
6. **Given** 稼働中のセッションが 10 本、**When** 過去の行を再開する、**Then** 今と同じく `session-limit` で拒否される

### User Story 2 - 止まった・失敗したセッションを自分の操作で再開できる (Priority: P1)

利用者は稼働中の区画で、終了済みの行や失敗した行 (supervisor の異常終了・`claude` のクラッシュなど) から「再開」を選び、同じ会話を続ける。

**Why this priority**: 失敗したセッションは今は閉じるしかなく、X-5 FR-013 は自動で再開しない。長い作業の途中で落ちたとき、文脈を失わずに戻れる経路が要る。

**Independent Test**: 1 ターン話したセッションを (a) 終了する (b) `claude` を外から止めて失敗にする、の 2 通りで止め、行の「再開」から続きを話せることと、元の行が消えることを確かめる。

**Acceptance Scenarios**:

1. **Given** 会話の id を持つ終了済みの行、**When** 「再開」から再開する、**Then** 新しい行が起きて選ばれ、元の行は閉じられる
2. **Given** 会話の id を持つ失敗した行 (`supervisor-exited` / `process-crashed` など)、**When** 「再開」から再開する、**Then** 同じ会話が続く。失敗した時点で書かれていたやり取りは残る
3. **Given** 最初の `system/init` の前に失敗した行 (会話の id が無い)、**When** 「やり直す」を選ぶ、**Then** 同じ起動設定を初期値にした新規起動のダイアログが開く
4. **Given** 失敗した行、**When** 利用者が何もしない、**Then** 今と同じく自動では再開しない
5. **Given** 中断しただけで `claude` が動いている行、**When** 行を見る、**Then** 「再開」は出ない (次のプロンプトを送れる)
6. **Given** 再開の起動が拒否された (上限・ランタイムが止まっている・claude が見つからない)、**When** 拒否の理由が出る、**Then** 元の行は残る

### User Story 3 - 引き継ぐ軸と選び直せる軸が分かる (Priority: P2)

利用者は再開のときに、フォルダ / ランタイム / Provider は元の会話のままであることを見て確かめ、モデル / effort / 権限モードを選び直してから再開する。

**Why this priority**: 軸を取り違えると会話が見つからないか、別の会話になる。選び直せる軸は、重い作業の続きをより強いモデルで行うなどの実際の使い方に要る。

**Independent Test**: 再開の形のダイアログで、引き継ぐ 3 軸が変えられず、選び直せる 3 軸が今の依存解決どおりに選べることを、WSL と Win32 の行で確かめる。

**Acceptance Scenarios**:

1. **Given** 再開の形のダイアログ、**When** 開く、**Then** フォルダ / ランタイム / Provider は表示だけで変えられない
2. **Given** 稼働中の行からの再開、**When** ダイアログを開く、**Then** モデル / effort / 権限モードの初期値は元の起動設定の値である
3. **Given** 再開の形のダイアログ、**When** モデルを変えて再開する、**Then** 再開したセッションは選んだモデル・effort・権限モードで動く (権限モードは安全 3 値のまま)
4. **Given** 元の起動設定のモデルが今の Provider で選べなくなっている、**When** ダイアログを開く、**Then** 今の依存解決と同じく選び直しを求める印が出る
5. **Given** 元の行の Provider・フォルダ・ランタイムがその後に削除・登録解除された、**When** 再開する、**Then** 理由つきで拒否され、軸を差し替えて続ける経路は出ない (分岐は X-6)

---

### User Story 4 - 再開したセッションでそれまでの会話が見える (Priority: P2)

利用者は再開したセッションの中央で、それまでの会話を上に、新しいやり取りを下に見る。

**Why this priority**: 続きを話すには直前の文脈が要る。過去ログの画面と行き来せずに済む。

**Independent Test**: tool の呼び出しを含む会話を再開し、中央にそれまでの会話が過去ログと同じ表示で出て、その下に新しい応答がストリーミングで足されることを確かめる。

**Acceptance Scenarios**:

1. **Given** 再開したセッション、**When** 中央を見る、**Then** それまでの会話が過去ログと同じ表示 (結果の無い tool は「結果不明」) で出て、その下に「ここから再開」の区切りがある
2. **Given** それまでの会話の部分、**When** 操作する、**Then** 読み取り専用で、承認や編集の操作は出ない
3. **Given** それまでの会話の読み取りが失敗した、**When** 再開する、**Then** 再開は進み、読み取りの失敗が中央に 1 行で出る (新しいやり取りは使える)

### Edge Cases

- `/clear` の後に再開した — X-9 は起動で最初に受けた `session_id` を使うので、`/clear` の前の会話が再開される。`/clear` の後の会話の id の扱いは X-6
- 同じ会話を Closta の外 (端末の `claude --resume`) で動かしている — Closta からは見分けられない。再開は止めず、記録が混ざりうることは利用者の責任とする
- 会話の transcript がその後に消された・壊れた — `claude` が会話を見つけられず起動が失敗する。失敗の理由で出す (理由のキーを足すか今のキーを使うかは plan で決める)
- 所在のディストロが止まっている過去の行 — 今どおり列挙されないので再開の対象にならない
- worktree の cwd の過去の行 — 登録フォルダに対応づかなければ未登録の行として扱う (U-3)
- ホストの config ディレクトリに、WSL の UNC の cwd (`\\wsl$\D\…`) で記録された過去の行 — どちらのランタイムの `claude` もその cwd では会話を探せないので、出自の不一致として理由つきで拒否する (FR-005)
- 再開の形のダイアログでプリセットを適用した — 選び直せる 3 軸だけに当て、引き継ぐ 3 軸は変えない
- 再開を連打した — 起動の受け付けは 1 回だけで、同じ会話の 2 本目は U-5 で拒否する
- 再開したセッションをさらに終了して再開する — 同じ会話の id で何度でも再開できる

## Requirements

### Functional Requirements

#### 再開の対象 (US-1 / US-2)

- **FR-001**: サイドバーの過去の区画の行は、FR-005 で軸が決まる行に「再開」の操作を出さなければならない。決まらない行は理由つきで押せない形で出す
- **FR-002**: 稼働中の区画の行は、`claude` が終わっていて (生存フラグが false) 会話の id を持つ行 (終了済み・失敗) にだけ「再開」を出さなければならない。`claude` が動いている行 (中断済みを含む) には出さない (U-8)
- **FR-003**: セッションスレッドは、SDK の `system/init` の `session_id` を UUID の形で検査して main に運び、main は稼働中の行の registry に会話の id として持たなければならない (U-1)。会話の id は永続化せず、ログに出さない。Closta の `sessionId` は再開でも新しく採る
- **FR-004**: 再開の起動は、会話の id を Agent SDK の `resume` の option で渡さなければならない。`QUERY_OPTION_KEYS` に `resume` を足し (11 → 12)、pin テストで固定する。会話の id は main の検証 (`validate.ts`) と agents の起動の値の検査の両方で UUID の形を確かめ、満たさなければ起動しない

#### 軸の引き継ぎと選び直し (US-3)

- **FR-005**: 過去の行の引き継ぐ軸は、列挙対象と行の cwd から決めなければならない — フォルダは行が対応づく登録フォルダ、ランタイムは列挙対象の所在 (ホスト → `Win32Runtime`、ディストロ → そのディストロの `WslRuntime`)、Provider は列挙対象の config ディレクトリに対応する登録済みの Provider (既定の config ディレクトリは Provider なし)。行の cwd の出自は、種類と名前空間が列挙対象の所在と一致しなければならない (ホストの記録はホストのパス、ディストロ D の記録は D から見た POSIX のパス。ホストの記録にある WSL の UNC の cwd・別のディストロの cwd は一致しない)。どれかが決まらない・一致しなければ、理由と直し方を出して再開を拒否する (U-3)
- **FR-006**: 再開は起動ダイアログを再開の形で開いて行わなければならない (U-2)。フォルダ / ランタイム / Provider は表示だけで変えられない。モデル / effort / 権限モードは今の依存解決 (AD-041) で選べる
- **FR-007**: 稼働中の行からの再開では、選び直せる 3 軸の初期値を元の起動設定の値にしなければならない。値が今の依存解決で選べないときは、今のダイアログの規則で選び直しを求める
- **FR-008**: 引き継ぐ軸が起動のときに解決できない (フォルダの登録解除・Provider の削除・ランタイムが到達不可) ときは、今の起動ゲートの理由で拒否しなければならない。引き継ぐ軸を差し替えて続ける経路を出さない (分岐は X-6)

#### 失敗した行と行の入れ替え (US-2)

- **FR-009**: 会話の id を持たない失敗の行には「やり直す」を出し、元の起動設定を初期値にした新規起動のダイアログを開かなければならない (U-6)。失敗したセッションを自動で再開しない (X-5 FR-013 のまま)
- **FR-010**: 稼働中の行からの再開の起動が受け付けられたら、元の行を閉じ、新しい行を選ばなければならない (U-4)。起動が拒否されたら元の行を残す
- **FR-011**: `claude` が動いている行が同じ会話の id を持つときは、再開を起動せず、その行を選ばなければならない (U-5)。判定は main の registry で行う (renderer の表示に頼らない)

#### それまでの会話の表示 (US-4)

- **FR-012**: 再開したセッションの中央は、それまでの会話を R-3 の読み取りの経路 (AD-034) で再開のときに 1 回読み、新しいやり取りの上に読み取り専用で出さなければならない (U-7)。表示は過去ログと同じ変換 (`live: false`) を使い、境目に区切りの行を 1 つ出す
- **FR-013**: それまでの会話の読み取りの失敗は再開を止めてはならない。中央に失敗を 1 行で出し、新しいやり取りは使えるままにする

#### 境界の検査・記録

- **FR-014**: 再開の起動は、新しい起動と同じ起動ゲート・同時実行数の上限 (10)・ランタイムの種類ごとの起動の値の組み立て (WSL は AD-041 (f)、Win32 は AD-058) を通らなければならない。再開のための分岐をランタイムの実装の外に置かない (Principle II)
- **FR-015**: query の options への `resume` の追加・会話の id を session thread から main に運ぶこと・X-5 FR-013 の「再開は X-6」の読み替えは ADR (AD-059。accepted) に書き、session charter の Related Specs / Related ADRs と Journey 4 の注記に記録しなければならない。完了の PR で roadmap の X-9 の行に結論を書く
- **FR-016**: 導入した用語 (再開・会話の id・再開の形のダイアログ) を glossary に反映し、`docs/ui-coverage.md` の Message branches の行の割当から resume (X-9) を外さなければならない (Principle XII / XIV)
- **FR-017**: 再開の起動で、最初の `system/init` が報告する権限モードが安全 3 値 (AD-041 (a)) の外 (または無い) ときは、セッションを `resume-failed` で失敗にして `claude` を止めなければならない (fail closed)。新しい起動の扱いは変えない (権限モードの強制は I-3)

### Key Entities

- **会話の id**: Claude Code の session id (UUID)。transcript のファイル名と同じ。稼働中の行は SDK の `system/init` から、過去の行は列挙の結果 (`SessionSummaryDTO.sessionId`) から取る。Closta の稼働中の行の `sessionId` とは別の値
- **再開の要求**: 会話の id・引き継ぐ 3 軸 (フォルダ / ランタイム / Provider)・選び直した 3 軸 (モデル / effort / 権限モード) の組。`SessionLaunchConfig` に会話の id を足した形にするか別の型にするかは plan で決める
- **稼働中の行の registry**: X-5 の sessionId → セッションの対応に、会話の id (無ければ null) を足したもの

### Assumptions

- Agent SDK の `resume` は、渡した cwd と config ディレクトリの組で transcript を探し、同じ会話の id のまま追記する (`forkSession` を渡さない限り)。quickstart で実機の記録を見て確かめる
- SDK は `resume` で過去のメッセージを stream に流さない。流れたときは `SDKUserMessageReplay` と同じく表示不要として扱い、それまでの会話は FR-012 の読み取りだけで出す
- Win32 で起動したセッションの記録はホストの config ディレクトリに書かれ、今の列挙と過去ログで読める (020 Assumptions。実機の確認は SC-007)

## Success Criteria

### Measurable Outcomes

- **SC-001**: WSL と Win32 のそれぞれで、過去の行・終了済みの行・失敗した行から再開した会話で、`claude` が前のターンの内容に答え、記録が同じ transcript に追記される — 計測経路: quickstart V-1 の実機 (本番ビルド。WSL のディストロと `C:\dev\closta` の両方)。合否: 6 通り全部が通ること。実機の確認の条件で、マージの条件ではない (下の「合否の扱い」)
- **SC-002**: 再開の起動の query の options が `resume` を含む 12 キーで、会話の id が UUID の形でないとき main と agents の両方で起動しない — 計測経路: `QUERY_OPTION_KEYS` の pin テスト + `validate.ts` の検証表のテスト + 起動の値の検査の単体テスト
- **SC-003**: 過去の行の軸の解決が、列挙対象の所在 × cwd の出自 (種類と名前空間) × config ディレクトリ × cwd の対応の全組み合わせで FR-005 のとおり (決まる・出自が所在と一致しない・未登録フォルダ・Provider が無い) になる — 計測経路: 軸の解決の単体テスト (表で回す)
- **SC-004**: 「再開」「やり直す」の出し分けが行の状態 (動いている・中断・終了済み・失敗で id あり・失敗で id なし・過去) の全部で FR-001 / FR-002 / FR-009 のとおりになる — 計測経路: 稼働中の区画と過去の区画のコンポーネントテスト
- **SC-005**: 再開の形のダイアログで引き継ぐ 3 軸が変えられず、選び直せる 3 軸の初期値が FR-007 のとおりで、プリセットの適用が引き継ぐ軸を変えない — 計測経路: 起動ダイアログのコンポーネントテスト
- **SC-006**: 稼働中の行からの再開で、受け付けたら元の行が閉じて新しい行が選ばれ、拒否されたら元の行が残り、同じ会話が動いているときは起動せずその行が選ばれる — 計測経路: main の起動の service の単体テスト (registry の会話の id) + E2E (偽の capability で再開と拒否を流す)
- **SC-007**: 再開したセッションの中央にそれまでの会話が読み取り専用で出て、読み取りが失敗しても新しいやり取りが使える。Win32 の会話が列挙と過去ログで読める (020 V-7 の引き継ぎ) — 計測経路: 中央のコンポーネントテスト (読み取りの成功・失敗) + quickstart V-2 の実機。合否: component テストの部分はマージの条件、V-2 の部分は実機の確認の条件 (下の「合否の扱い」)
- **SC-008**: 既存の起動・列挙・過去ログのテストと Constitution 検証が通る — 計測経路: `docs/discovery.md` の verify (CI と同じコマンド)
- **SC-009**: 再開の起動の最初の `init` が安全 3 値の外の権限モードを報告したら `resume-failed` で失敗し、`claude` が止まる。昇格の権限モードで作った会話を再開しても、実効の権限モードは選んだ安全 3 値である — 計測経路: セッションスレッドの単体テスト + quickstart V-9 の実機。合否: 単体テストの部分はマージの条件、V-9 の部分は実機の確認の条件

**合否の扱い**: 2 つの条件を分ける。

- **マージの条件** — SC-002〜SC-006・SC-008 と、SC-007 / SC-009 の自動の計測経路 (component テスト・単体テスト) が緑であること (tasks SH-011 の verify)
- **実機の確認の条件** — SC-001 (quickstart V-1 の 6 通り)・SC-007 の V-2・SC-009 の V-9 が実機で通ること。実機を行えたら結果を `quickstart-results.md` と roadmap の X-9 の行に書く。行えなかったときは `quickstart-results.md` に「未実施」と書いてマージし、X-9 の行に未確認の項目として残して利用者の実機に送る (2026-10-21 夜間の規則)。実機で通らなかったときは利用者に返す
