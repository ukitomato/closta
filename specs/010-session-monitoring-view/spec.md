# Feature Specification: セッション監視ビュー (O-1)

**Feature Branch**: `010-session-monitoring-view`

**Created**: 2026-10-02

**Status**: frontmatter の `status:` を正とする

**Input**: User description: "O-1 セッション監視ビュー (session ドメイン、roadmap M3 の順 10、依存 X-5)。X-5 で入った単一 supervisor・上限 10・状態通知 (SessionStatusUpdate) と、assistant-ui ThreadList ベースの稼働中セッション一覧を土台に、10 セッションを俯瞰できる監視ビューを作る。M3 の達成状態「10 セッションを俯瞰でき、未表示情報がゼロ」に向けた最初の feature。X-5 から繰り越した、charter KPI「並列時の滑らかさ」の実機計測 (10 本が同時に応答を流す中での入力) をこの feature で行う。"

## Summary

X-5 の**稼働中セッション一覧 (サイドバー)** を、10 本を俯瞰できる**監視ビュー**に育てる。

- 承認待ちと失敗を、表示していないセッションでも**見逃さない**形で示す。
- 各行に、今の状態になってからの**経過時間**と**直近の活動** (承認を求めている tool 名・呼び出した tool 名・本文の先頭 1 行) を出す。枠を占める本数 (例: 8/10) を常に示す。
- **compact / comfortable** の情報密度を切り替えられる。compact では 10 本が 1 画面に収まる。
- charter KPI「並列時の滑らかさ」を、**実 `claude` 10 本**が同時に応答を流す中で実機計測する (X-5 SC-003 からの繰越)。

**なぜ今**: M3「差配できる」の達成状態は「10 セッションを俯瞰でき、未表示情報がゼロ」である。X-5 で 10 本を並行に回せるようになったが、一覧は状態の文字列だけで、どれが利用者を待っているかを探す必要がある。charter Journey 3「承認待ちのセッションが目立つ形で示される」を満たす。

## 本 feature の位置づけ

- **作り変えない (USER 決定 2026-10-02)。** 全面の監視画面は新設せず、X-5 の `RunningSessionList` (サイドバー) を拡張する。没入ビューは X-5 の画面 (サイドバー + transcript) のままで、charter Journey 3 の「一覧 ⇄ 没入」は「サイドバーの行を選ぶ ⇄ 次の行を選ぶ」で成立させる。
- **renderer だけの feature である。** 行に出す情報はすべて renderer が既に持つもの (X-5 FR-008 の全セッションの本文保持・状態通知) から導く。IPC・状態通知 (`SessionStatusUpdate`)・supervisor は変えない。X-5 FR-004 の「状態通知に会話由来の文字列を載せない」は維持する。
- **稼働中セッション一覧 (監視ビュー) は session の操作 UI である** (USER 決定 2026-10-02 design-gate R2。ui charter の「他 domain の一覧・操作 UI は各 domain が持つ」に揃える)。行の形・強調の出し方は本 feature で決める。承認カードと transcript の見た目・element 選定は `ui` domain の領分のまま。session charter の Out of scope の記述を本 feature で改める (FR-013)。

継承する規則の正本は先行 feature / ADR に置き、本 spec は参照形で書く (`## Dependencies`)。

## User Scenarios & Testing

### User Story 1 - 承認待ちと失敗を見逃さない (Priority: P1)

利用者は別のセッションを見ている最中でも、どのセッションが承認を待っているか・失敗したかが一覧で分かる。承認待ちの件数が常に見え、セッション画面の中ではそこから承認待ちのセッションへ 1 操作で移れる。セッション画面以外 (過去セッションの一覧など) を開いている間も、承認待ちと失敗の件数はナビに出る。

**Why this priority**: charter Journey 3 の 2 番目「承認待ちのセッションが目立つ形で示される」そのものである。承認待ちを見逃すとそのセッションは止まったままになり、並列で回す意味が失われる。

**Independent Test**: 一覧の component テストで、表示中ではないセッションが承認待ちになったときの強調・件数・移動を確認する。

**Acceptance Scenarios**:

1. **Given** 5 本が稼働中で A を表示中、**When** B が承認待ちになる、**Then** B の行が承認待ちとして強調され (色だけに頼らない)、一覧の見出しに承認待ちの件数 1 が出る。行の並びは変わらない
2. **Given** 承認待ちが 2 本 (B が先、C が後に承認待ちになった)、**When** 見出しの承認待ちの件数を押す、**Then** 先に承認待ちになった B が表示中になり、B の承認カードが見える。もう一度押すと C に移る
3. **Given** B の承認に応じた、**When** B が応答中に戻る、**Then** B の強調は消え、件数が 1 減る
4. **Given** 表示していない D が失敗する、**When** 一覧を見る、**Then** D の行が失敗として強調され、理由キーの文言が出る (承認待ちとは別の見た目)。D の行がスクロールの外にあっても、見出しに失敗の件数 1 が出る
5. **Given** 表示していないセッションが承認待ちまたは失敗になる、**When** スクリーンリーダーを使っている、**Then** その遷移が 1 回だけ読み上げられる (応答中 ⇄ 応答待ちなどの他の遷移は読み上げない)。同じ更新で 2 本が遷移したときは 1 つの文にまとめて読まれる
6. **Given** 過去セッションの一覧など、セッション画面以外を開いている、**When** 稼働中の B が承認待ちになる (B が直前までセッション画面で選んでいたセッションでも同じ)、**Then** ナビの「セッション起動」に承認待ちの件数 1 が出て、その遷移が 1 回だけ読み上げられる。セッション画面に移ると B の行が強調されている。D が失敗したときは、ナビに失敗の件数 1 が承認待ちとは別に出る

### User Story 2 - 各セッションが何をしているか一覧で分かる (Priority: P1)

利用者は一覧を見るだけで、各セッションが今何をしていて、その状態がどれだけ続いているかが分かる。枠をいくつ使っているかも見える。

**Why this priority**: 状態だけでは「応答中のまま 10 分止まっている」「何の承認を求めているか」が分からず、結局すべてを開いて回ることになる。俯瞰の中身にあたる。

**Independent Test**: 行の情報を作る純関数の単体と、一覧の component テストで確認する。

**Acceptance Scenarios**:

1. **Given** B が 2 分前から応答中で、最後のメッセージが `Edit` の呼び出しで終わっている、**When** 一覧を見る、**Then** B の行に経過時間 (2 分) と直近の活動 (`Edit` と入力の先頭) が出る
2. **Given** B が `Bash` の承認を求めている、**When** 一覧を見る、**Then** B の行の直近の活動に承認を求めている tool 名 (`Bash`) と入力の先頭が出る
3. **Given** B が応答を終えて次のプロンプトを待っている、**When** 一覧を見る、**Then** B の行の直近の活動に最後の本文の先頭 1 行が出る
   - **Given** B にプロンプトを送った直後で、まだ応答が無い、**When** 一覧を見る、**Then** B の行の直近の活動に送ったプロンプトの先頭 1 行が出る
4. **Given** 直近の活動に HTML やマークダウン、改行、非常に長い文字列が含まれる、**When** 一覧を見る、**Then** plain text の 1 行として既定の長さで切り詰めて出る (描画も解釈もしない)
5. **Given** 枠を占めるセッションが 8 本 (うち 1 本は起動中)、**When** 一覧の見出しを見る、**Then** 「8/10」の形で枠の使用数が出る。`claude` が終わったセッションは数えず、起動要求の応答を待っている 1 本は数える
6. **Given** 枠が 10/10、**When** 一覧を見る、**Then** 新規起動の導線の近くに、上限に達していることと枠の空け方 (X-5 の `session-limit` の拒否文言と同じ内容) が示される。起動要求の拒否は X-5 の `session-limit` のまま

### User Story 3 - 情報密度を切り替えて 10 本を 1 画面に収める (Priority: P2)

利用者は一覧の情報密度を compact と comfortable で切り替えられる。compact では 10 本が 1 画面に収まり、comfortable では直近の活動まで読める。

**Why this priority**: 俯瞰と詳細はトレードオフであり、10 本では comfortable のままだとスクロールが要る。ただし US-1 / US-2 が成り立てば価値は出るので P2 とする。

**Independent Test**: 一覧の component テストで切り替えと各密度の表示項目を、E2E で compact の 10 行が 1 画面に収まることを確認する。

**Acceptance Scenarios**:

1. **Given** comfortable で 10 本が稼働中、**When** compact に切り替える、**Then** 各行は 1 行 (状態・作業フォルダの表示名・経過時間と、同じ段に行の操作) になり、ウィンドウが既定の大きさのとき 10 行がスクロールなしで見える
2. **Given** compact、**When** 承認待ちや失敗のセッションがある、**Then** compact でも US-1 の強調と件数は同じに出る
3. **Given** compact、**When** 行にフォーカスまたはポインタを当てる、**Then** comfortable で出る情報 (ランタイム・起動時刻・直近の活動) を読める
4. **Given** 密度を切り替えた、**When** 別のセッションに切り替える・新しいセッションを起動する、**Then** 選んだ密度は保たれる

---

### User Story 4 - 実 `claude` 10 本が応答を流す中でも入力が滑らか (Priority: P2)

10 本の実セッションが同時に応答を流し、監視ビューの各行が更新され続けていても、表示中のセッションの composer への入力は遅れない。

**Why this priority**: charter KPI「並列時の滑らかさ」の実機側の計測であり、X-5 SC-003 で E2E (偽の supervisor 接続) までしか測れていない部分を埋める (X-5 pr-gate R1 po M-002 の繰越)。監視ビューは行の更新を増やすので、その負荷込みで測る。US-1〜US-3 が動けば価値は出るので P2 とするが、**2 feature にわたる繰越であり、本 feature の範囲から削らない**。(**2026-10-02 改訂**: SC-005 は有効な回 0 件で利用者が閉じ、残りは roadmap O-3 の「義務 (O-1 から)」(2) に移した。FR-012 の改訂の行)

**Independent Test**: CI の E2E (X-5 の負荷を経過時間と直近の活動を出した状態で流す) と、実機の計測手順 (実 `claude` 10 本) で確認する。

**Acceptance Scenarios**:

1. **Given** comfortable で 10 本が X-5 SC-003 の負荷を流している (偽の supervisor 接続)、**When** 表示中のセッションの composer に打鍵する、**Then** X-5 SC-003 の閾値を満たす
2. **Given** ビルドした実アプリで、実 `claude` 10 本がメッセージを継続的に流している (FR-012 の有効な回の条件を満たす)、**When** 表示中のセッションの composer に打鍵する、**Then** 同じ閾値を満たし、その値が記録として残る

### Edge Cases

- 承認待ちのセッションが表示中のセッション自身だけである → 強調と件数には含める。件数のボタンは押せない状態にし、移れる先が無い理由 (表示中のセッションが承認を待っている) を示す
- 承認待ちの件数を押した先のセッションが、移る直前に承認待ちでなくなった → 移った先で承認カードが無いだけで、エラーにはしない
- 失敗したセッションが溜まる → 強調と見出しの失敗の件数は利用者が閉じるまで残る。失敗の件数は押せない表示で、承認待ちの件数とは分ける
- 起動直後で状態通知がまだ届いていない (`launching`) → 経過時間は起動からの時間、直近の活動は空
- 直近の活動の元になる本文がまだ無い (最初のプロンプト待ち) → 直近の活動は空で、状態 (プロンプト待ち) だけを出す
- 直近の活動の元になる本文・入力が文字列でない、または双方向制御文字・行区切り文字を含む → 例外を投げず、空または 1 行の plain text に倒す (一覧の描画を落とさない)
- 直近の活動の本文が短時間に何度も更新される (20 件/秒) → 行の表示の更新は間引く (US-4 の閾値を壊さない)
- 経過時間が長い (数時間) → 時間単位までの短い表記で出す
- 終了済みのセッションが溜まる → 件数の上限は設けない (X-5 の判断を維持。一覧の末尾に置くなどの並べ替えも行わない)。compact で 1 行に縮むことで俯瞰を保つ
- 枠の使用数が main の判定と瞬間的に食い違う → 一覧の表示は renderer が持つセッションと起動要求中の 1 件から、main と同じ規則 (domain の数え方) で数える。残る食い違いは `claude` の終わりの通知が届くまでの間に限り、起動の可否は main が正である
- renderer の再読み込み → X-5 FR-014 のとおり全セッションが止まり、一覧は空から始まる。選んだ密度は既定に戻る
- 実機計測の回が有効な回の条件 (FR-012) を満たさなかった → その回は無効として理由キーだけを記録し、再計測する
- 実機計測の有効な回で閾値を割った → feature を止め (pr-gate に進まない)、原因の切り分けを記録して利用者が判断する。閾値や有効な回の下限を黙って緩めない
- 作業フォルダの表示名がまだ引けない (一覧の読み込み前・失敗) → 読み上げの文と行は固定の代替語を使い、文が壊れない

## Requirements

### Functional Requirements

#### 承認待ちと失敗の強調 (US-1)

- **FR-001**: 一覧は、承認待ち (`awaiting_permission`) の行を**表示中かどうかにかかわらず**強調しなければならない。
  - 強調は色だけに頼らない (アイコンまたは文言を伴う。WCAG 2.1 AA 1.4.1)。
  - 行の並びは変えない (起動順のまま。行が飛ぶと押し間違いを生む)。
- **FR-002**: 一覧の見出しは、承認待ちのセッションの**件数**を常に示し、それを押すと、**表示中を除く承認待ちのうち、承認待ちになったのが最も早いもの**へ表示を切り替えなければならない。
  - 承認待ちになった時刻は renderer が状態の遷移を受けた時刻とする (FR-005 と同じ起点)。
  - 移れる先が無いとき (承認待ちが 0 本、または表示中の 1 本だけ) は押せない状態にし、理由を示す。
  - **グローバルのナビの「セッション起動」にも承認待ちの件数を出す** (USER 決定 2026-10-02。セッション画面以外を開いている間も見える)。件数が 0 のときは出さない。ナビの件数は表示だけで、押したときの移動は持たない (ナビはセッション画面に切り替えるだけ)。
- **FR-003**: 一覧は、失敗 (`error`) の行を承認待ちとは別の見た目で強調し、理由キーの文言 (X-1 / X-5 の理由キーの訳出。compact では短い訳。FR-008 の追記) を行に出さなければならない。一覧の見出しには**失敗の件数**を押せない表示で出す (USER 決定 2026-10-02。行がスクロールの外にあっても気づける)。ナビの「セッション起動」にも、承認待ちの件数とは別に失敗の件数を出す (USER 決定 2026-10-02 design-gate R2)。
- **FR-004**: **見ていないセッション**が**承認待ちまたは失敗に遷移した**ときは、支援技術に 1 回だけ通知しなければならない (polite な live region。他の遷移は通知しない)。
  - 「見ているセッション」は、セッション画面が表示されていて、かつ選ばれているセッションだけとする。セッション画面以外を開いている間は、選ばれていたセッションも通知の対象にする。
  - live region は**アプリ全体の寿命**に置き、セッション画面以外を開いている間の遷移も通知する。
  - 同じ更新で複数のセッションが遷移したときは 1 つの文にまとめる。同じ文が続いても読み上げられるようにする。
  - 通知の文は作業フォルダの表示名と固定の文言だけとし、**会話由来の文字列 (tool 名・入力・本文) を含めない**。

#### 行の情報 (US-2)

- **FR-005**: 各行は、**今の状態になってからの経過時間**を示さなければならない。
  - 起点は renderer がその状態への遷移を受けた時刻とし、状態通知の前の `launching` は起動の時刻とする。
  - 表記は 1 分未満は秒、1 時間未満は分、それ以上は時間と分 [ASSUMED]。表示の更新は 1 秒ごとまでとする。
- **FR-006**: 各行は、**直近の活動**を 1 行の plain text で示さなければならない。直近の活動は、renderer が保持するそのセッションの本文と承認要求から、次の優先順で導く。
  1. 承認待ちなら、承認を求めている tool 名と入力の先頭
  2. 応答中で、最後の assistant メッセージの末尾が tool の呼び出しなら、その tool 名と入力の先頭 (live 表示には tool の結果が載らないため、tool が実行中か終わったかは区別しない)
  3. 最後のメッセージが利用者のプロンプトなら (送った直後)、そのプロンプトの先頭 1 行
  4. それ以外は、最後の assistant メッセージの本文の先頭 1 行 (text の part を順に見て、最初に得た空でない行)
  - 「先頭 1 行」は最初の空でない行とし、既定の長さ (80 文字 [ASSUMED]) で切り詰める。双方向制御文字・行区切り文字は除く。HTML・マークダウンとして解釈しない (X-1 の XSS 境界を回帰させない)。
  - 4 種の会話由来の部分には固定の前置き (承認を求めている / 実行 / 送信 / 応答) を付け、状態の文言とは別の要素で出す (会話由来の文字列が状態の表示に紛れないようにする)。
  - 本文の更新ごとに行を再描画しない。直近の活動の更新は 1 行あたり毎秒 2 回までに間引き、間引きは行の購読より手前で行う [ASSUMED]。最後の値は必ず反映する。
- **FR-007**: 一覧の見出しは、**枠を占めるセッションの本数と上限** (「8/10」の形) を常に示さなければならない。
  - 数え方は main の上限判定と同じ domain の規則 (X-5 FR-005 の「枠を占める」。`claude` の生存フラグで数え、`done` / `interrupted` / `launching` / 生存中の `error` を含む) を使い、起動要求の応答を待っている 1 件を足す。
  - 上限に達しているときは、新規起動の導線の近くに上限に達していることと枠の空け方を示す。空け方の文言は X-5 の `session-limit` の拒否文言を正本とし、書き写さない。新規起動の導線は無効にしない (起動の可否は main が判定する。X-5 FR-005)。

#### 情報密度 (US-3)

- **FR-008**: 一覧は **compact / comfortable** の 2 つの情報密度を持ち、利用者が切り替えられなければならない。
  - comfortable: X-5 の行の情報 (作業フォルダの表示名・ランタイム・起動時刻・状態) に、経過時間と直近の活動を加える。
  - compact: 状態・作業フォルダの表示名・経過時間を 1 行で示す。ウィンドウが既定の大きさのとき 10 行がスクロールなしで収まり、全角を含む長い表示名でも行の操作が行の外へ押し出されない (Principle VIII)。
  - どちらの密度でも FR-001〜FR-004 の強調・件数・通知と、行の操作 (X-5 FR-011 の終了・停止・閉じる) は同じに出す。
  - compact で行から外してよいのはランタイム・起動時刻・直近の活動であり、行へのフォーカスまたはポインタで読める。**隔離状態 (isolation charter Journey 2 のバッジ。I-x で導入) は compact でも行に出す** (置き場を残す)。
  - **追記 (利用者決定 2026-10-03、pr-gate R1 po M-002 の対応)**: compact の失敗の行は、状態の印の横に**短い理由** (理由キーの短い訳) を出し、理由の全文と終了の告知 (X-5 FR-011 の強制終了 / 強制停止) は、行へのフォーカスまたはポインタ (ツールチップ) と読み上げで読める。短い理由は行の幅を広げない
- **FR-009**: 選んだ密度は、セッションの切り替え・起動・終了を通して保たなければならない。既定は comfortable、アプリの再起動と renderer の再読み込みでは既定に戻る [ASSUMED — 永続化は持たない]。

#### 境界の維持

- **FR-010**: 本 feature は renderer の中で閉じなければならない。
  - IPC のチャネル・状態通知 (`SessionStatusUpdate`) のフィールド・preload・supervisor・main・domain を変えない (domain の既存の規則を使うのはよい)。状態通知に会話由来の文字列を載せない規則 (X-5 FR-004) を維持する。
  - 行の情報は、X-5 FR-008 で renderer が保持する本文と状態通知から導く。導出は純関数に置き、一覧の行は本文全体を購読しない (表示に使う値だけを選ぶ。X-5 SC-003 の対策を崩さない)。

#### 並列時の滑らかさの計測 (US-4)

- **FR-011**: X-5 SC-003 の E2E を、**comfortable で経過時間と直近の活動 (本文の分岐) を出した状態**で流し、同じ閾値を満たさなければならない (USER 決定 2026-10-02)。
  - 強調 (承認待ち・失敗) と tool の分岐は E2E の負荷に含めない。E2E の偽 supervisor は承認待ち・失敗・tool の呼び出しを流さず、流すように変えると main に差分が出る (FR-010)。これらの描画は component テスト (SC-001 / SC-002) と実機計測 (FR-012) で見る。
- **FR-012**: charter KPI「並列時の滑らかさ」の**実機計測の手順**を用意し、本 feature の中で 1 回の計測機会に 3 回測って記録しなければならない (X-5 SC-003 / pr-gate R1 po M-002 の繰越)。
  - ビルドした実アプリ (E2E の stub ではない本物の composition) を自動操作で起動し、実 `claude` 10 本にメッセージを継続的に流させている間に、表示中のセッションの composer に打鍵して、X-5 SC-003 と同じ指標 (入力遅延の p95・long task の最大。50ms 超の件数は記録のみ) を取る。負荷は応答の長さではなくメッセージの数で作る (live 表示はメッセージ単位で更新されるため)。
  - **有効な回の条件**: 30 秒の計測の窓の全期間で 10 本が応答中 (承認待ち・応答待ち・失敗が 0 本) であり、窓の中で届いたメッセージが 30 件以上 (当初の [ASSUMED] は 100 件。1 回目の実測で 30 秒に 40 件しか届かず、実 `claude` は tool を 1 回呼ぶたびに数秒かかるため、**利用者判断 2026-10-02 で 30 件に下げた**。E2E の負荷 (毎秒 200 件) との比を記録する。さらに変えるときは閾値と同じく利用者に諮る)。満たさない回は無効とし、理由キーだけを記録する。
  - **観測点**: 一覧は、各行の状態 (行の状態の値) と、全セッションの受信メッセージの累計数 (会話由来の文字列を含まない数値) を、画面の属性として読める形で出す。計測はこれだけを読む。本番の画面にストアそのものを外から読める口は作らない。
  - 手順は CI に載せない (実 `claude` のトークンを使い、WSL の実行環境と登録済みの Provider を要するため)。CI・E2E の stub の環境では走らずに失敗で止まる。**agent は利用者の明示的な指示があるときだけ実行する**。手順書と計測の自動化スクリプトを残し、結果を quickstart-results に記録する。
  - **完了条件** (USER 決定 2026-10-02 design-gate R2): 有効な回が 3 回 quickstart-results に記録されるまで pr-gate / done に進まない。有効な回で閾値を割ったら feature を止めて利用者が判断する。
    - **改訂 (2026-10-02)**: 7 回測って有効な回は 0 件だった。利用者が、記録した事実とともに SC-005 を閉じ、この完了条件を外した (SC-005 の実施結果と quickstart-results の V-3 を参照)。残した宿題は roadmap の O-3 の「義務 (O-1 から)」が持つ。
  - 記録・出力に会話由来の文字列・env を含めない (失敗時に Playwright が書く error-context の aria snapshot を含む。pr-gate R1 security H-001)。例外の文も理由キーと件数だけにする。計測は承認カードに応答しない。
  - 有効な回の下限は有限の正の数でなければ失敗で止め、受信の累計が読めない回は `probe-missing` で無効にする。使った下限と、既定から変えたかを記録する (pr-gate R1 architecture M-002)。

### Key Entities

- **監視ビュー**: X-5 の稼働中セッション一覧を拡張したもの。強調・件数・経過時間・直近の活動・情報密度を持つ。新しい画面ではない
- **直近の活動**: 行に出す 1 行の plain text。renderer が保持する本文と承認要求から導く (FR-006)。状態通知には載らない
- **状態に入った時刻**: renderer が各セッションの状態の遷移を受けた時刻。経過時間 (FR-005) と承認待ちの順 (FR-002) に使う。renderer の保持の中だけにある
- **情報密度**: compact / comfortable。renderer の表示状態であり、永続化しない
- **枠の使用数**: main の上限判定と同じ規則で数えた、枠を占めるセッションの本数 (起動要求中の 1 件を含む) と、上限 10 の組 (X-5 の同時実行数の上限)
- **没入ビュー**: charter Journey 3 の語。本 feature では、表示中セッションのペイン (X-5 の transcript と composer) を指す

## Success Criteria

- **SC-001**: **承認待ちと失敗を見逃さない。** どちらの密度でも、承認待ちの行がすべて強調され (色以外の手掛かりを伴う)、一覧の見出しとナビの承認待ちの件数が承認待ちの本数と常に一致し、件数を押すと FR-002 の規則の行へ移って承認カードが描画され、移れる先が無ければ押せない。失敗の行は承認待ちと別の見た目で理由が出て、見出しとナビの失敗の件数が失敗の本数と一致する。見ていないセッション (FR-004) の承認待ち・失敗への遷移の通知は 1 遷移 1 回 (同じ更新の複数の遷移は 1 つの文) で、他の遷移では 0 回。セッション画面以外を開いている間は、選ばれていたセッションの遷移も通知される。通知の文に会話由来の文字列が 0 件で、表示名が引けないときも文が壊れない。計測経路: 導出の純関数の単体 + 一覧・ナビ・live region・セッション画面の component テスト (状態通知の連続遷移を与える)
- **SC-002**: **行の情報が正しく、安全に出る。** 経過時間・直近の活動 (FR-006 の優先順の各分岐)・枠の使用数 (main と同じ domain の規則の結果と一致し、起動要求中を 1 件足す) が期待どおりに導かれる。HTML・マークダウン・改行・双方向制御文字・行区切り文字・長大な文字列・非文字列を含む入力で、直近の活動は例外を投げずに 1 行の plain text (または空) になり既定長で切れる (要素として描画されるものが 0 件)。計測経路: 導出の純関数の単体 + 一覧の component テスト
- **SC-003**: **compact で 10 本が 1 画面に収まり、密度が保たれる。** 既定のウィンドウサイズで compact の 10 行がスクロールなしで見え、行に横あふれが無く行の操作が行の内側にあり、compact でも強調・件数・行の操作が出て、切り替え・起動・終了で密度が保たれる。計測経路: E2E (10 本を起動して compact の行の位置と幅を確かめる) + 一覧の component テスト + 全角の長い表示名での目視 (quickstart V-4)
- **SC-004**: **監視ビュー込みで X-5 SC-003 の閾値を保つ。** comfortable で経過時間と直近の活動を出した状態で、X-5 SC-003 の負荷 (10 本 × 20 件/秒 × 1KB × 30 秒、うち 1 本に上限いっぱいの part) を流す間に、composer の入力遅延 p95 50ms 以下・renderer の long task の最大 100ms 未満。50ms 超の件数は記録のみ。計測経路: E2E (`e2e/multi-session.spec.ts` の計測を、経過時間と直近の活動が出ていることを確かめたうえで流す)
- **SC-005**: **実 `claude` 10 本でも滑らか (charter KPI の実機計測)。** ビルドした実アプリで、FR-012 の有効な回の条件を満たす回が 3 回あり、そのすべてで SC-004 と同じ閾値を満たす。各回の計測値と計測条件を記録し、無効になった回は理由キーを記録する。記録してよい項目はこの SC の許可リストに限る: 入力遅延 p95・long task の最大と件数・窓の中のメッセージ数・窓の始まりと終わりに応答中だった本数・有効 / 無効と理由キー・プロンプトの識別子・モデル (既定のモデルなら `default`)・ウィンドウサイズ・composition が本物であること・使った有効な回の下限と、既定から変えたか (`minMessages` / `thresholdOverridden`。pr-gate R1 で追加)・後始末が kill に落ちたことの合図 (`teardown=killed`。そのときだけ。pr-gate R2 で追加)・各回の後の `wsl.exe` と WSL 内 `claude` の数。本 feature の完了条件である (FR-012。2026-10-02 に改訂して外した — FR-012 の改訂の行)。計測経路: FR-012 の実機計測の手順 (自動化スクリプト + quickstart-results への記録)。**実施結果 (2026-10-02)**: 7 回計測して有効な回は得られず (実 `claude` が窓の途中で応答を終える)、**利用者判断で締めた** — 手順を直した後の 4 回は入力遅延 p95 13.6〜14.9ms・long task 0 件。詳細と残す宿題は quickstart-results の V-3
- **SC-006**: **境界が変わらない。** `src/main`・`src/preload`・`src/agents`・`src/domain` の差分が 0 件 (IPC のチャネル・状態通知のフィールドを含む) で、X-5 の状態通知の全フィールド走査 (会話由来の文字列 0 件) が緑のまま。一覧の行が本文の配列そのものを購読せず、状態を変えずに本文を 500ms の間に 20 回更新したとき、行本体の描画が 3 回以下 (経過時間の時計による描画は経過時間の表示だけに閉じ、数に含めない)。計測経路: `git diff --name-only` による差分の確認 (quickstart V-5) + X-5 の既存テスト + 行の描画回数を数える component テスト

- **OS の通知・タスクバーのバッジ・音** → 持たない。承認待ちの通知はアプリ内 (一覧の強調・件数・ナビの件数・支援技術への通知) に限る
- **直近の活動の tool ごとの整形 (対象のファイル名やコマンドの先頭語だけを出すなど)** → O-2 (tool ごとの表示を決めるときに再検討する。tool の入力の先頭に秘密が出うる点もそこで扱う)
- **情報密度の永続化** → 持たない ([ASSUMED])
- **一覧の並べ替え・絞り込み・検索** → 持たない。検索は O-3
- **終了済みセッションの件数の上限・自動で閉じる** → 持たない (X-5 の判断を維持。FR-013 で結論を記録する)
- **Tool group の既定 open 化** ([AD-035](../../docs/decisions/0035-tier-a-tool-display-and-subagent-nesting.md) の O-1 候補) → transcript の描画であり `ui` domain。O-2 の Tier A 完全化で扱う
- **上限の設定変更・待ち行列・失敗したセッションの再開** → 持たない / X-6
- **承認カードと transcript の見た目・element 選定** → `ui` domain (監視ビューの行の形は本 feature が決める。本 feature の位置づけ)
