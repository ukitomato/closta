### [Critical] 到達可能な登録フォルダを登録解除する導線が設計のどこにも無く、FR-031 が案内する手順を利用者が実行できない (C-001)

- **観察**: FR-017 は「**解除の導線を示すのは「到達不可」のエントリだけ**とする」と定め、FE-022 が「登録解除の導線は「到達不可」のときだけ出す」でこれを実装条件に落としている。data-model §6 も同じ規則を不変条件として書く。一方 FR-031 は越境時の手順に「**旧エントリの登録解除**を含める」と定め、`CrossBoundaryStep` に `unregister-old-folder` を置き、quickstart は「手順に旧エントリの登録解除が含まれること (SC-006)」を検証項目にしている。越境するフォルダは第 3 段で `reachable` であるから、**利用者が案内どおり推奨先へ配置し新規登録したあと、旧エントリには解除の導線が出ない**。US-2 の AS も「**到達不可なエントリ**を登録解除する」しか持たない。結果、**誤って登録したフォルダ・作業が終わったフォルダを利用者が一覧から外す経路が存在しない** (〜50 件規模を想定)。
- **同種事象探索**: `登録解除|unregisterFolder|解除` で **16 件**。このうち **`reachable` なエントリに解除操作を与える記述は 0 件**。`unregisterFolder(id)` は能力としては存在するが、**呼び出す UI 経路を与えた記述が 0 件**。
- **リスク/影響**: (a) 越境案内 (SC-006 が「例外なく」提示を要求する手順) が**実行不能な指示**になる。(b) 登録は一方向にしか増えず、間違えて登録したフォルダが恒久的に残る。**フォルダを実際に削除すれば `unreachable` になって解除できる**という逆立ちした回復経路しか無い。US-2 の価値が壊れる。
- **推奨アクション**: FR-017 を「**解除を勧める表示 (推奨・強調) を出すのは `unreachable` のときだけ**とし、解除操作そのものはすべてのエントリに提供する」に分解する。FE-022 の条件も同じ 2 層に書き分ける。US-2 に「到達可能なエントリを登録解除できる」AS を 1 本追加し quickstart V-2 に 1 ステップ挿入する。round 3 H-001 の意図 (WSL2 の自動停止で毎日削除を勧めない) は「勧める表示」側の限定だけで満たされ、**操作の提供を止める必要はない**。
- **根拠**: FR-017 / FR-031 / SC-006 / US-2 AS-8 / US-3 AS-17、`runtime` charter Actors

### [Critical] `path-not-mapped` が第 3 段にあるため、未マップのドライブ × 停止中 / 判定中のランタイムに「起動して再検出せよ」と案内し、従うと選択肢が無言で消える (C-002)

- **観察**: 第 1 段は所在 `windows` の行を 3 列とも第 2 段へ通す。第 2 段は `stopped` を `blocked` (`distro-not-running`)、`running`+`idle/probing` を `blocked` (`capabilities-not-probed`) とし、**どちらもパスの接頭辞を見ない**。`path-not-mapped` の判定は第 3 段にしか無い。したがって **未マウントドライブ / ネットワークドライブに登録したフォルダ × 停止中の `WslRuntime`** は `blocked` として選択肢に現れ、文言「ディストロが停止している。**起動して再検出すると使える**」が提示される。指示どおり起動して再検出すると第 3 段で `unreachable` (`path-not-mapped`) になり、FR-028 により**選択肢から消える**。判定中の場合も文言は「完了すると使える」であり、完了した瞬間に消える。これは §8「順序を固定する理由」が**防ぐと宣言した harm そのもの**であり、FR-029 が禁じた事象である。
  quickstart V-3 は同一セル (未マップドライブ × 停止中) に対して「**選択肢に現れ**、『起動する』『再検出する』が示される」と「**選択肢に現れない**」という**互いに排他な期待値**を書いている (round 3 C-001 と同じ形)。さらに US-3 AS-13 は「到達不可として選択肢に現れず、**理由が示される**」を要求するが、FE-030 が理由提示を義務づけるのは「**到達可能なランタイムが 0 件のとき**」だけで、他に到達可能なランタイムがある通常ケースで理由が出る経路は無い。**消えた理由を利用者が知る手段が無い**。
- **同種事象探索**: `path-not-mapped` で **4 件**、うち**第 2 段との適用順序に言及するものは 0 件**。`未マウント|ネットワークドライブ|マッピングに無い|マッピングに現れない` で **14 件**、うち**停止中・判定未完了と組んだセルを扱ったものは 0 件**。BE-051 の網羅セルにも該当セルは **0 件**。
- **リスク/影響**: 利用者は (a) 使えない組み合わせのために**ディストロ起動という環境操作を無駄に行い**、(b) 完遂した直後に選択肢が消え、(c) **理由も次の操作も提示されない**行き止まりに着く。US-3 AS-9「案内を見た利用者が起動して再検出すると**同じ組み合わせが解決される**」が定義上破れる。未マウントドライブ・マップ済みネットワークドライブは Windows 11 の実運用で普通に存在し、WSL2 のアイドル自動停止と組み合わさるため例外環境ではない。**round 3 で Critical と判定した harm が、修正によって別の入口から戻っている**。
- **推奨アクション**: 第 3 段の材料 (マッピング) は probe 前に得られないため**順序の入れ替えでは閉じない**。(1) `distro-not-running` / `capabilities-not-probed` の文言から「使える」という断定を外し「**起動して再検出すると、この組み合わせを使えるかどうかが分かる**」に改める。(2) 「**利用者が `resolutionSteps` を実行した結果 `unreachable` に確定した組み合わせは、選択肢から消すと同時にその理由を提示しなければならない**」を FR-028 に追加し US-3 に AS を 1 本足す (これは AS-13 の「理由が示される」を初めて拘束する)。(3) quickstart の該当行に限定を付け、停止中起点のステップを追記。BE-051 に網羅セルを追加し FE-032 に 1 ケース足す。SC-007 に「消えた理由の提示」を含める。
- **根拠**: FR-028 / FR-029 / FR-047 / SC-006 / SC-007、US-3 AS-9・AS-13、`runtime` charter Journey 2、AD-016

### [High] SC-008 の拘束句が US-4 の 3 本にしか及ばず、同じ構造の AS が 3 本残っている。quickstart V-4 は拘束句に追随していない (H-001)

- **観察**: round 3 の修正で SC-008 に「US-4 の AS が「止まる」と明記する経路は群を問わず全数検出される — `require()` (AC-4)、分割代入・ブラケット記法 (AC-5)、引数配列 (AC-7)」が入った。しかし違反サンプル群 (b) には**同じく US-4 が無条件に「止まる」と書いている経路**がまだ 3 本残っている。(i) AS-3「`ui` から `domain` 経由で node builtin に**推移的に到達する**」、(ii) AS-8「許可リストの外から `wsl.exe` / プロセス起動 API を呼ぶ」、(iii) AS-5 の「**等価な API** も含む」(SC-008 が名指すのは分割代入・ブラケット記法のみ)。3 本とも SC-008 が採用した根拠 (「SH-013 / SH-014 が実装対象としており未検出を許容しない」) が**そのまま当てはまる**。さらに quickstart V-4 は依然として群 (b) の記述しか持たず、**SC-008 の新しい拘束句を検証する行が存在しない**。
- **同種事象探索**: US-4 の AS 12 本を群 (a) / (b) へ照合すると、群 (b) 側に落ちて拘束力のある SC を持たない AS が **3 件**。quickstart V-4 内で SC-008 の全数検出を群 (b) の一部に要求する行は **0 件**。
- **リスク/影響**: `ui` → builtin の推移到達は FR-035 が名指した本 feature の主要要件であり、許可外プロセス起動は Principle VI の要である。どちらも「期待表に未検出と書き次の feature ID を割り当てる」だけで SC-017 が緑になり **R-1 が完了できる**。加えて quickstart V-4 は実機検証の手順そのものであり、追随していない以上 SC-008 の新条項は**手順上検証されない**。
- **推奨アクション**: SC-008 の列挙に AS-3 / AS-8 / AS-5 の等価 API を加える。tasks の注記を同じ 3 本まで広げる。quickstart V-4 の表に「群 (b) のうち **SC-008 が全数検出を求める部分** → 全数検出」の行を追加し、既存の群 (b) 行を「残余」に限定する。実装側は既に対象としているため追加コストは無い。
- **根拠**: US-4 AS-3 / AS-5 / AS-8、FR-035 / FR-037 / FR-041、SC-008 / SC-017、SH-012 / SH-013 / SH-014 / SH-020 / SH-021

### [Medium] `probe-failed` が一覧画面に存在せず、判定に失敗したランタイムが「判定中」と区別できないまま放置される (M-001)

- **観察**: round 3 の修正で `probeState: failed` が data-model に入り、解決画面では `BlockedReason: probe-failed` として文言と解消手順 (`rescan-runtimes`) を持つ。ところが **US-1 の一覧画面側には落ちていない** — FE-010 が表示対象に挙げるのは「capabilities / 未判定 / 判定中 / seccomp の 3 値 / 不足依存」であり `failed` が無く、quickstart V-1 にも**判定失敗の行が無い**。US-1 AS-5 は安全側解釈だけを拘束しており表示の区別は求めていない。
- **同種事象探索**: `probe-failed|判定失敗` で **7 件**。うち**一覧画面での提示を定めたものは 0 件**。quickstart V-1 に判定失敗の期待行 **0 件**。
- **リスク/影響**: 判定の途中失敗は spec 自身が Edge Case に挙げる想定内の状態である。利用者は一覧上で「いつまでも判定中のまま」に見えるランタイムを前に待てば終わると誤解する。FE-011 の「再検出」は常設のため完全な行き止まりではないが、**解決画面では「再検出すると試し直す」と案内される同じ状態が、主画面では原因も次の操作も示されない**という画面間の不整合になる。
- **推奨アクション**: FE-010 の表示対象に「判定失敗 (再検出の導線つき)」を加え quickstart V-1 に 1 行追加する。SC-003 は値の一致しか見ないため拘束は quickstart 行で足りる。
- **根拠**: US-1 AS-5 / FR-003 / FR-047、`runtime` charter「`capabilities` を正直に表明する」
