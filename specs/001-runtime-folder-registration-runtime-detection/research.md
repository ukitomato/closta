# Phase 0 Research: フォルダ登録とランタイム検出 (R-1)

**Spec**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md) | **Date**: 2026-09-14

前提となる調査は **SPIKE-8 / SPIKE-9 / AD-023 の scaffold 検証で完了済み**である。
本ファイルは (a) 既決事項のうち設計を直接縛るものと、(b) 本 feature で新たに決めた方式を記録する。
**R-1 で再調査してはならない項目**を明示することが目的の半分を占める。

## R-01: ディストロ一覧の取得 — 3 つの列挙を並列に 1 回ずつ

**Decision**: 名前だけの列挙 / 実行中だけの列挙 / 詳細列挙を**並列に 1 回ずつ**呼ぶ。
役割は **名前 = 名前列挙** / **実行状態 = 実行中列挙との積集合** / **バージョン = 詳細列挙**の三分割。

**Rationale**:

- `wsl.exe` の固定起動コストは約 1.5 秒 (AD-015)。ディストロごとに呼ぶと 4 台で 6 秒を超え
  SC-004 を満たせない。3 つは独立プロセスなので並列実行でき、壁時計は約 1.6 秒。
  **ディストロ数に比例しないため AD-015 §2 に抵触しない**
- 詳細列挙は状態を**ロケールに応じて翻訳する**。文字列一致で判定すると環境依存で壊れる。
  実行中だけの列挙は名前しか返さないため翻訳の影響を受けない
- 詳細列挙の出力は列整形されており、**空白を含むディストロ名を空白区切りでトークン化すると
  名前が切れる**。名前の正本は名前だけの列挙とする
- バージョンは行から既知の名前を最長一致で取り除いた残りから読む。
  「行内の最初の数値」では `Ubuntu-26.04` で誤読する

**Alternatives**: 詳細列挙のみ + 状態文字列の多言語テーブル (ロケールは無限に増える) /
レジストリ直読み (実行状態を持たず、非公開の実装詳細) /
実行中だけの列挙のみ (停止中が消え charter KPI を満たさない)。

**実装上の制約** (AD-015 §4): UTF-8 出力を要求しないと出力が UTF-16LE になり検出が丸ごと失敗する。
改行は CRLF のままなので末尾の復帰文字を除去する。詳細列挙のヘッダ行は翻訳されるので読み飛ばす。

## R-02: capability 判定とマッピング取得を 1 呼び出しに統合する

**Decision**: **実行中であることを確認済みの**ディストロ 1 つにつき 1 回だけ
ディストロ内でスクリプトを実行し、**capability 判定の材料とマウントマッピングを同時に取得**する。
ディストロ間は並列。スクリプトは**引数ではなく標準入力で渡す**。

**Rationale**:

- どちらも `wsl.exe` を必要とし固定コスト 1.5 秒を払う。分けると 1 台あたり 3 秒になる。
  AD-015 §2「複数の情報が要るときは 1 回の呼び出しにまとめる」の直接適用
- **`wsl.exe` の引数処理はバックスラッシュを消す** (AD-015 §5)。これはパス固有ではなく
  引数処理そのものの性質であり、整形コマンドを引数に含めると**静かに壊れた形で実行される**。
  標準入力で渡せば引数処理を通らない
- ログインシェルを経由しない。必須依存の確認に必要なコマンドは標準のパスにある。
  AD-015 §7 の「`claude` はログインシェルの PATH にしかない」は**起動 (X-1) の話**である

**取得するもの**: 必須依存の解決パス / 非特権 user namespace の制限状態と確認コマンドの終了状態 /
user namespace の実地作成結果 / マウント情報 / **完了の標識**。

**必須依存の解決パスをマウントマッピングと突き合わせる。**
WSL は既定で Windows の PATH を Linux 側に追加するため、Windows 側の実行ファイルが
`command -v` で見つかりうる。これを「存在する」と扱うと、Linux 側に必須依存が無いまま
sandbox ありと表明される。AD-015 §8 は該当の依存を**必須**と定めており、
その場合 sandbox は実際には成立しない。

**除外条件に特定のマウント位置を書いてはならない。** マウント位置は設定で変更でき、
`/mnt/` を条件に書くと変更した環境で偽陽性が通る。マッピングは同じ呼び出しで
取得済みなので、**マッピングを先に確定させてから依存の判定を行う**(順序制約)。

**マウント情報はファイルシステム種別で絞らない** (AD-015 §6)。正本は
マウントオプションが示すドライブ対応である。WSL の実装は変遷しており、
種別で絞ると未知の種別の環境でマッピングが空になり、Windows 側フォルダが
すべて変換不能になる。

**取得した情報の整形はホスト側で行い、スクリプト側で加工しない。**
スクリプトに含めるコマンドを最小に保ち、内容の検証を成立させるためである。

**拡張点 (I-1)**: 項目単位の出力なので、docker endpoint の検出は項目を 1 つ足すだけでよい。
全ディストロの再走査は不要 (AD-012 Consequences)。

## R-03: seccomp フィルタの検出は保留し「未判定」として表現する

**Decision**: 3 値で保持し、**R-1 では常に「未判定」を返す**。sandbox の可否には影響させない。

**Rationale**:

- AD-015 は seccomp フィルタを**任意依存**と明記し「無くても sandbox は動作する」と実地確認している
- 一方で「`capabilities` では区別できる形にしておくことが望ましい」とも述べており、
  **型としては持つべき**である
- 検出方法は AD-015 に記載がなく**裏取りできていない**。推測で実装すると常に「なし」を返す
  ルールができ、それは**判定していないものを「ない」と表明する**ことになる

**Follow-up**: I-3 の前に検出方法を確定する。R-1 は型の器だけを用意する。

## R-04: 停止中ディストロは起動しない — 約束ではなく型で表す

**Decision**: 停止中ディストロは**一覧に出す**が capabilities とマッピングは未取得とし、
検出のためにプロセスを起動しない。利用者がアプリ外で起動し**明示的な再検出**を行った時点で判定する。
この制約を、**実行状態の確認を経た値しか受け取れない型**で構造化する。

**Rationale**:

- 停止中ディストロを対象にコマンドを実行するとディストロが起動する。
  利用者が意図しない起動は Principle VI の姿勢と整合しない
- 一覧から消す案は charter KPI「検出の網羅」を満たさない
- **「呼ばない」という約束だけでは不十分**である。IPC の入口は複数あり、UI を無効化しても
  UI 以外の経路が残る。型で受け取れなくすれば、迂回はコンパイルで止まる
- **実行状態はキャッシュ値であり実体と乖離する。** WSL2 はアイドルのディストロを
  自動停止するため、キャッシュが「実行中」のまま実体が止まっている窓が常時存在する

**確認の頻度** (FR-010): 確認自体が 1.5 秒かかるため、**操作回数に比例させてはならない**。
判定バッチでは全ディストロ分を一括で 1 回、フォルダブラウズではセッション単位で再利用する。
UNC 経由のディレクトリ一覧は 22 ms (AD-015 §1) であり、そこに毎回 1.5 秒を前置すると
UNC を選んだ判断が無意味になる。

**帰結**: 停止中ディストロを所在とするフォルダは変換後パスを表示できない。
マウント位置を仮定した暫定表示は FR-024 に反するため採らない。
**「起動が必要」と、起動後に再検出する導線を示す** (FR-018)。

**「起動 / 停止の継続的な検知」は Out of Scope とする。** WSL にイベント API は無く、
定期ポーリングは AD-015 §2 と衝突する。操作直前の状態確認で代替する。

## R-05: 越境と到達可能性は「所在 × ランタイム × 実行状態」で決める

**Decision**: 作業フォルダに**所在を登録時に明示的に持たせ**、越境判定と到達可能性判定を
所在・ランタイム・マウントマッピングから決める。**実測は行わない。**

**Rationale**:

- 所在を先に選ばせる導線にすることで「このパスはどの名前空間のものか」という推測が**入口で消える**
- AD-016 の実測は「Linux 側のプロセスが Windows 側のファイルシステムを読む」構図そのものの
  コストであり、**決定論的に判定できる**。追加 I/O はゼロ
- 実測ベースの判定は初回登録をブロックし、かつ**閾値の根拠が R-1 時点で無い**
- 越境を**選択不可にしない**のは AD-016 §2 の明示的な決定

**所在が WSL でも、パスが当該ディストロの Windows マウント配下なら越境とする。**
フォルダブラウザは所在配下のみを辿るため、利用者は Windows 上のフォルダを
所在 WSL として登録できる。判定に必要なマッピングは既に手元にある。

**到達可能性は 3 値とする。** 「到達できない」と「一時的に解決できない」は
利用者にとって別の状態であり、後者は選択肢に出して解消手順を示さなければ詰まる。
`WslRuntime` のアイドル自動停止は日常的に起きる。

**所在 WSL × `Win32Runtime` を到達不可とする根拠**: UNC 経路は AD-015 で
**ファイル読み取り経路**として検証されているが、ネイティブ Windows プロセスの
作業ディレクトリとして与える経路は検証されていない。charter の
「そのランタイムから到達できないフォルダは選択肢に現れない」に従う。

判定表は [data-model.md](data-model.md) §8 を正とする。

## R-06: パス変換はマッピングを 1 回取得しホスト側で計算する

**Decision**: マッピングを R-02 の統合呼び出しで 1 回取得し、
以後の個々の変換は**ホスト側の純粋関数**で行う。

**Rationale**: AD-015 §6。変換ごとに外部コマンドを呼ぶと 1 回 1.5 秒かかり成立しない。
マウント位置は設定で変更できるため決め打ちできない。

**名前空間を 3 つに分ける。** ホスト (ドライブレター形式) / ランタイム内部 (POSIX) /
WSL への UNC 経路は、変換規則が互いに異なる。1 つの型に同居させると、
UNC への変換をマッピング由来の変換に通そうとして「マッピングに無い」で失敗する。

**ランタイム名前空間のパスは識別子を実行時に保持する。** 識別子はディストロ検出の
結果として実行時に決まる値であり、静的な型として扱えない。型パラメータで表現しても
実運用の値ではすべて同じ型に潰れ、別ディストロ間の取り違えを検出できない。
**変換 API の入口で識別子の一致を検証する**のが唯一の防御である。

**マッピングを名前空間のペアとして一般化する。** ドライブレターを鍵に固定すると、
I-1 の 2 ホップ目 (WSL → コンテナ) が両端にドライブを持たないため表現できない。
接頭辞のペアにすれば同じ型で書け、合成で多段を表せる (AD-004 Consequences の要求)。

**照合はパスセグメント境界で行い、複数一致なら最長を採る。** 文字列の前方一致では
`/mnt/cdrom` が `/mnt/c` に一致する。マウント位置を `/` 直下にした構成では
通常の Linux ディレクトリが片端から誤変換の対象になる。

## R-07: レイヤ境界は ESLint と dependency-cruiser で見る

**Decision**: AD-023 §7 に従い両方を使う。

| ツール | 見るもの |
|---|---|
| ESLint | **直接** import。編集時フィードバック |
| dependency-cruiser | **推移的**依存・グラフ全体・循環・**`require()` 形式** |

直接違反は両方が検出しうる。役割が違うのは「見られる形」であって対象ではない。

**パス操作モジュールの制限は dependency-cruiser にも置く。** `require()` 形式は
ESLint の import 制限の対象外であり、本プロジェクトは preload を CommonJS で出力するため
`require()` が自然に書かれる箇所が実在する。グラフを解決する層でなければ塞げない。

**`ui` から node builtin への推移的到達を禁止する。** `ui → domain` の純粋関数呼び出しを
許可した以上、`domain` 経由で builtin に届く経路が生じる。renderer は sandbox 下で
builtin を解決できない。ESLint は直接 import しか見ないため、この経路は
dependency-cruiser でしか塞げない。

**I/O 禁止リストは `node:` 接頭辞付きの別名も含める。** 接頭辞なしの名前だけでは取りこぼす。
パス操作モジュールはこのリストに含めない (文字列操作であり I/O ではない)。許可制限は別ルールとする。

**状態を持つ調停クラスから I/O モジュールへの直接依存を禁止する** (AD-023 §7)。
AD-023 §5 はこれを「肥大化への唯一の歯止め」と位置づけている。

## R-08: Principle II / VI の検証は許可リスト方式にする

**Decision**: 検証スクリプトを実装し、**許可リスト**で管理する。

**Rationale**:

- Constitution は「文字列リテラル一致では不十分」と明記している。コマンドが
  **引数配列**で構成されるとリテラルが現れずすり抜ける (AD-012)
- Constitution が指定する許可ディレクトリは **AD-023 のレイヤ構成に存在しない**。
  固定値で埋め込むと後続 feature で再び食い違う
- **特定のサブコマンドだけを禁じるのは不十分**である。環境を変える操作は複数あり、
  列挙漏れが必ず生じる。**必要なものだけを許す**ほうが短く、将来の追加に自動で対応する

**検証項目**:

| # | 内容 | Principle |
|---|---|---|
| 1 | 特権コマンド文字列の不在 (**Linux / Windows 両方**。引数配列も捕捉) | VI |
| 2 | `wsl.exe` に渡す引数が許可リスト内であること | VI |
| 3 | `wsl.exe` を名指せるモジュールの許可リスト | VI |
| 4 | docker CLI を名指せるモジュールの許可リスト (R-1 では**空**) | VI |
| 5 | 許可モジュール内にイメージ構築サブコマンドが無いこと | VI |
| 6 | ディストロ内で実行するスクリプトが定義済みの内容と一致すること | VI |
| 7 | プロセス起動 API を使えるモジュールの許可リスト | VI |
| 8 | 注記のないプラットフォーム分岐の不在 (**等価な API と構文変形を含む**) | II |
| 9 | **OS へのプロトコル関連付け API の呼び出しの不在** (SC-016 後段) | VI |
| 10 | **CSP が FR-040 の directive 集合を満たし、かつ `unsafe-inline` / `unsafe-eval` を含まないこと** (SC-016)。**開発用の CSP 定義も走査対象に含め、除外リストへ移さない** | — (FR-040) |
| 11 | **`setWindowOpenHandler` の存在と、送信元 origin 定数が 1 つであること** (SC-016) | — (FR-039 / FR-040) |

**許可リストの正本は検証スクリプト内の定数とし、追加には ADR を要する** (FR-041)。
Constitution 側はこのファイルを参照する形にする。

**項目 9 が別立てなのは、項目 1 が捕捉するのが「特権コマンド文字列」だからである。**
OS へのプロトコル関連付けは Electron の API 呼び出しであり、コマンド文字列としては現れない。
レジストリを書くため Principle VI に抵触する (R-13)。SC-016 の後段はこの項目で計測する。

**検証スコープは `src/` と `scripts/` に加えビルド構成を含める** (FR-037)。
本 feature はプロジェクトで初めて `package.json` の scripts / CI 定義 /
パッケージング設定を作る。これらは実行されるが、`src/` だけを見る検証では対象外になる。
`scripts/constitution/` 自身も実行可能コードであり、検証の外に置かない。
Windows ホスト側の永続化 API (レジストリ書き込み・ログイン項目の設定) も同様に禁止対象とする。

**除外はファイル単位の明示リストとする。** ディレクトリ単位の除外を作ると、
そこに後から実行可能コードが増えたときに検証が構造的に届かなくなる —
Constitution v1.1.0 が Principle II でディレクトリ除外を捨てたのと同じ理由である。
唯一の例外は違反サンプル置き場 `tests/rule-fixtures/` で、これは
**ルール検証ランナーが検査対象へ展開する入力**であり通常検証のスコープ外である
(SC-009 が「違反サンプルを保持したまま違反 0 件」を要求するため、この位置づけを明記しないと成立しない)。

**項目 8 は識別子の直接参照だけでは足りない。** 等価な API と、分割代入・ブラケット記法による
構文変形を含める。import で塞げる経路 (標準モジュール経由) は import 制限と二層にする。
**許可ディレクトリは実名で定義する。**

**項目 6 をコマンド名の許可リストで書いてはならない。** 出力系コマンドとリダイレクトの
組み合わせでディストロ内に永続的な変更を残せるため、コマンド名を許すと形が許されてしまう。
**スクリプトそのものを定義済みの内容に固定し、その一致で検証する。**

**項目 6 は等値検査だけでは足りない。** 定数に文字列を連結して書き込めば
「定数が存在する」検査を通過する。項目 6 は次の 3 点を検査する — (i) 定数が単一のリテラルで
あること、(ii) 標準入力へ書く式が定数の識別子そのものであること、
(iii) 定数の内容が許可するコマンド形の allow-list に収まること。

**それでも定数の内容が Principle VI に反するかは機械では判定できない。**
一致検証が見るのは形であって意味ではない。
定数と実行箇所を同じ PR で書き換えれば、永続的な変更を残すスクリプトが**全項目**を通過する。
**モジュール許可リストと同じく、定数の内容の変更には ADR を要する**ものとし、
定数には「**ディストロ内に永続的な変更 (ファイル・パッケージ・OS 設定) を残さない。
プロセス寿命で消える一時資源の生成は許す**」「標準入力を読まない」を不変条件として付す
(contracts/runtime-detection.md C-3)。**この 2 つは ADR レビュー (人間) が担保するものであり、
機械検証されない。** 「読み取りのみ」と書かないのは、AD-015 §8 の判定 4 が
user namespace を実際に作成するためである — 文言が自己矛盾していると
レビュー時の判定基準が失われる。

## R-09: 登録フォルダの永続化は JSON、ディレクトリのパスは注入する

**Decision**: ユーザデータディレクトリ配下の JSON ファイルに保存する。
**ディレクトリのパスは `app` レイヤが解決し `infra` に引数で渡す。**
SQLite は本 feature で導入しない。

**Rationale**:

- R-1 が持つ永続データは所在・パス・表示名・登録日時のみで、クエリも結合も不要
- SQLite はネイティブモジュールであり Electron の ABI に合わせた再ビルドが要る (AD-009 / AD-013)。
  R-1 で導入するとパッケージングの検証範囲が広がり SPIKE-13 第 1 段階の切り分けが難しくなる。
  roadmap も「Agent SDK を 1 つ入れて 1 回通す」としている
- **ディレクトリの解決には Electron API が必要だが `infra` は `electron` の許可ディレクトリではない**
  (FR-038 / AD-023 §8)。素直に書くと**同じ feature で作る lint ルールが自分の実装を止める**。
  値を `app` で解決して注入すれば許可リストを緩めずに解決できる
- 同じ理由で、所在 `windows` のフォルダピッカーも `app` レイヤに置く。
  所在 WSL は UNC 列挙なのでピッカーを使わない

形式と復元規則は [contracts/workspace-store.md](contracts/workspace-store.md) で定義する。

## R-11: assistant-ui は design system の土台としてのみ導入する

**Decision**: 公式 CLI を R-1 で実行し、スタイル基盤とトークンを置く。
**chat 用の Element は採用しない。**

**Rationale**:

- AD-023 の「採用する公式手順」は scaffold と assistant-ui の 2 ステップで 1 組であり、
  R-1 がプロジェクト初期化を担う以上ここに属する
- Principle XIII は独自トークンの追加を禁じる。R-1 は UI を持つため、
  トークンの土台が無い状態で書くと独自トークンを足すか R-3 で塗り直すかになる
- SPIKE-2 (Element の導入コスト実測) は transcript 表示の話であり別物

**導入直後に Principle XIII の検証条件を確認する。** 検証条件は特定の設定ファイルを
参照しているが、公式 CLI の生成物がその形とは限らない。ファイルが無ければ検証が空振りし、
生成物が検出パターンに一致すれば導入直後に閾値を破る。**生成物を見てから条件を追随させる。**

**自作コンポーネントの根拠を実名で残す。** AD-019 は element 総数を 202 種とし
59 要素が未分類と明記している。「対応する element が存在しない」と断定する前に、
一覧・状態表示に転用しうる候補を実名で照合し、不適合の理由を書く。

## R-12: パス操作の経路を `AgentRuntime` の公開面として定義する

**Decision**: Constitution Principle I が要求するパス操作の経路を `AgentRuntime` の
プロパティとして定義し、実装は `domain` の純粋関数に置く。
**パス操作の標準モジュールを import してよいのはこの実装モジュール 1 つだけ**とする。

**Rationale**:

- Principle I の Statement は API の存在を前提にしている。charter と `_overview.md` も
  同じ表記を cross-domain invariant として掲げる
- 標準モジュールの import をディレクトリで制限するだけだと、制限の外で
  パス合成を必要とするモジュールが**実装不能になる**。API を提供して初めて制限が成立する
- **AD-004 と AD-023 が矛盾していた。** AD-004 は「変換の責務は `AgentRuntime` の内側」、
  AD-023 は「パス変換は `domain`」と述べる。**公開面が `AgentRuntime`、実装が `domain` の
  純粋関数**という形で両方を満たす。この調停は AD-025 に記録する
- ホスト名前空間の操作も同じモジュールが公開する。これで `infra` / `app` が
  ホスト側のパスを組む経路が閉じる

**実装モジュールはプラットフォームによって挙動が変わる API を使わない。**
ホスト名前空間とランタイム名前空間で意味論が異なり、実行環境で結果が変わってはならない。
このモジュールは `domain` にあり、ホスト OS に依存してはならない (Principle II)。

## R-13: renderer はカスタムプロトコルで配信し CSP を絞る

**Decision**: アプリ内で登録したカスタムプロトコル経由で配信し、CSP を絞る。
**OS へのプロトコル関連付けは行わない。**

**Rationale**: AD-023 は assistant-ui の Electron セキュリティ要件を「全面的に採用する」と
宣言している。R-1 は scaffold とウィンドウ生成を固定する feature であり、
ここで決めないと既定 (`file://`、CSP 未設定) が以降の全 feature の土台になる。

**開発ビルドでも同じ要件を満たす。** dev サーバから配信する場合はその origin を
送信元の許可集合と CSP の directive に含める形で満たし、**環境で検証を無効化する分岐を作らない**。
`unsafe-inline` / `unsafe-eval` は開発時も禁じる。無効化の分岐は出荷物でも条件 1 つで外せる形になり、
緩い CSP を検証の除外リストへ移せば機械検証そのものが消える。

OS へのプロトコル関連付けはレジストリを書くため Principle VI に抵触する。
アプリ内登録で本要件は満たせる。
