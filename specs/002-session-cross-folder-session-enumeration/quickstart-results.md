## V-0: 列挙プロセスの単独起動 (SH-094 / Principle VII / AD-010)

**日付**: 2026-09-17 (初版) / **2026-09-18 に再実施** (AD-030 でプロトコルが変わったため)
**手段**: `electron-vite build` の出力 `out/main/enumerate-sessions-*.js` を
**Electron を介さず `node` で直接起動**し、**標準入力に要求の行を流して**
標準出力の 1 行を読む。

```
echo '{"kind":"enumerate","version":2,"id":99,"targetKey":"host#0",
       "configDir":"...","scope":{"kind":"page","limit":3,"offset":0}}' |
  node out/main/enumerate-sessions-<hash>.js
```

環境変数は **`SystemRoot` / `TEMP` の 2 つだけ**を与えた
(`ENUMERATION_ENV_ALLOWLIST`。**config ディレクトリは要求の行に載る**。AD-030 §2)。

| 確認項目 | 結果 |
| --- | --- |
| バンドルが `electron` を require するか | **0 件**。`require("@anthropic-ai/claude-agent-sdk")` の 1 件のみ |
| 終了コード | `0` |
| 標準出力 | 行区切り JSON 1 行。`kind` / `version` / `targetKey` が期待どおり |
| 標準エラー | **空** |
| ホストの config ディレクトリ | 成立 |
| **WSL の config ディレクトリ (UNC 経路)** | **成立** |
| **新プロトコルでの再確認 (2026-09-18)** | **成立**。1,076 ms で応答し、要求の `id` が echo された |

**標準入出力の経路だけで成立している。** Principle VII Statement 後半
(「単独起動でき、標準入出力経由でプロトコルを話せる形を保つ」) を、
機械検証ではなく**実際の起動**で確認した — `parentPort` は import を伴わないため
ESLint にも依存グラフにも現れず、**機械検証が緑でも守れていない形になりうる**
([AD-028](../../docs/decisions/0028-session-enumeration-process-and-unc-handoff.md) Consequences)。

**AD-030 §5 で `parentPort` の経路が加わった**が、選択は `src/agents/transport.ts` の
1 モジュールに閉じてあり、**本体は経路を知らない**。
この確認は標準入出力側の経路が生きていることを測っている。

## 実装時の再測定 (H-021 の履行)

design-gate の H-021 は「SC-008 の予算が research 内部で 3 倍ぶれる。
**実装中に実測し直す**」を残していた。その再測定である。

**条件**: 実バンドル + 実 config ディレクトリ。1 回の列挙ごとに**冷えた子プロセス**を起こす
(AD-028 §1 の「要求 1 回」の寿命。**プロセス再利用による短縮を含まない**)。

| 対象 | scope | 所要 | 件数 | programmatic | worktree を含む `cwd` |
| --- | --- | --- | --- | --- | --- |
| ホスト既定 | 全件 | 1,330 ms | 51 | 8 | 3 |
| ホスト既定 | 先頭 50 | 1,262 ms | 50 | 8 | 3 |
| WSL (Ubuntu-26.04) | 全件 | **3,309 ms** | **276** | **40** | 7 |
| WSL (Ubuntu-26.04) | 先頭 50 | **1,823 ms** | 50 | 0 | 1 |

### 読み取れること

**1. `programmatic` の 2 回列挙は正しく効いている。**
WSL 全件の 40 件は [research.md](research.md) R-09 の実測 (269 件中 40 件) と一致する。
`SDKSessionInfo` にこの項目は無く、`includeProgrammatic` は**フィルタであって区別子ではない**
(design-gate L-002) ため、既定の結果と除外した結果の**差集合**で決めている。

**先頭 50 件で 0 件なのは誤りではない。** 2 つの結果は同じ順序で並び、
除外側は既定側の部分列であるため、既定側の先頭 N 件の所属は除外側の先頭 N 件で決まる。
この config ディレクトリでは programmatic なセッションが古い側に寄っていた。

**2. 支配的な費用は子プロセスの起動と SDK の import である。**
research R-01 は「冷えた子プロセスで import + 1 回の列挙 = 2,171 ms」を測っていた。
本測定の WSL 先頭 50 件が 1,823 ms であり、**2 回列挙を含めてなお当時の単発測定より速い**。
つまり 2 回列挙の追加費用は、起動費用に比べて小さい。

**3. SC-008 の予算に対する余裕は小さい。**

| SC-008 の要求 | 実測 | 判定 |
| --- | --- | --- |
| 先頭 50 件の**描画**が 2 秒以内 | 列挙だけで 1,823 ms (WSL) | **余裕が約 180 ms しかない** |
| 1 所在あたり 700 件規模の全件が 10 秒以内 | 276 件で 3,309 ms | 外挿で約 8.4 秒。**予算内だが余裕は小さい** |

**[RISK — 2026-09-18 に決着]** 先頭 50 件の予算は、列挙が終わってから描画するなら満たせない。
**実測でそうなった** (3 所在で 4,537 ms)。
予告どおり**予算ではなく描画の開始点を見直し**、所在ごとの段階描画にした
(本ファイル下部「人間判断 (2026-09-18) — 描画の開始点と計測の単位」)。
結果は `list-sessions-first-rows` 1,841 ms / 予算 2,000 ms で **ok**。

**[ASSUMED]** いずれも開発ホスト 1 台の実測である (spec の `## Assumptions` と同じ限界)。

## SH-074: SC-008 の計測 (実機 / 開発ビルドの計測ログ)

**日付**: 2026-09-18
**手段**: `npm run dev` で起動し、画面から「セッション」を開く。
main が出力する計測ログの値で判定する (SC-008 の計測経路)。

### 実機の値

| 計測点 | 実測 | 予算 | 判定 |
| --- | --- | --- | --- |
| `list-sessions-verify` (内訳) | 1,631 ms | — | 実行状態の確認 (`wsl.exe` の固定費) |
| `list-sessions-discover` (内訳) | 1,673 ms | — | うち探索そのものは**約 40 ms** (verify を含む値) |
| **`list-sessions-enumerate`** (内訳) | **10,653 ms** | — | **ここが支配的** |
| `list-sessions-first-page` | **12,331 ms** | 2,000 ms | **OVER** |
| `list-sessions-all` | 12,695 ms | 10,000 ms | **OVER** |
| `list-sessions-cached` | **0 ms** | 100 ms | **ok** |

**キャッシュヒットの条件だけは満たしている。**

### 到達までに直した 2 件のバグ (どちらも実機でしか出ない)

| 症状 | 原因 | 修正 |
| --- | --- | --- |
| 先頭ページが毎回 **32 秒** | 子プロセスが応答を書いても**終了しない**。`utilityProcess` は親との接続がイベントループを保持する。素の `node` では終了するため **SH-094 の単独起動確認では成立していた** | 応答の 1 行で確定して子を終了させる。標準エラーも読み捨てる (読み手のいないパイプが埋まると子が書き終えられない) |
| 先頭ページの取得が **2 回**走る | `loaded` は取得の**完了後**に立つため、開発ビルドの二重 effect で 2 本目がキャッシュに当たらない (実測 7,743 ms と 7,390 ms が並んだ) | 実行中の先頭ページ取得に合流させる |

### 子プロセス 1 件あたりの費用 (Electron の `utilityProcess`)

捨てのスクリプトで `utilityProcess.fork` から**最初の応答が届くまで**を測った。

| 条件 | 実測 |
| --- | --- |
| ホストの config ディレクトリ 1 件だけ (取得 2 件) | **2,506 ms** |
| ホストの config ディレクトリ 1 件だけ (取得 50 件) | **2,710 ms** |
| WSL の config ディレクトリ 1 件だけ (UNC。取得 50 件) | **4,193 ms** / 2 回目 4,104 ms |
| ホスト + WSL を**同時**に 2 件 | ホスト 2,880 ms / WSL **10,470 ms** |
| 3 件を**同時** | 2,952 ms / 10,022 ms / **11,419 ms** |

### 読み取れること

**1. 予算 2 秒は、子プロセス 1 件だけでも届かない。**
ホストの config ディレクトリから 2 件取るだけで **2,506 ms** かかる。
内訳のほとんどは **Electron の utility process の起動と SDK の import** であり、
列挙そのものではない (同じバンドルを素の `node` で走らせると合計 1,262 ms)。
**「所在が 1 つでも 2 秒に収まらない」**ので、対象を減らしても並べ替えても解決しない。

**2. 並行に起こすと遅くなる。**
WSL 単独 4,193 ms が、ホストと同時に起こすと **10,470 ms** になった (2.5 倍)。
contracts C-6 は「異なる列挙対象は並行して実行してよい」と許しているが、
**実測では許すだけで得にならない** — utility process の起動が資源を食い合う。
直列 (2,710 + 4,193 = 約 6.9 秒) のほうが速く、ばらつきも小さい。

**3. research R-01 の前提は素の `node` の値だった。**
「冷えた子プロセスで import + 1 回の列挙 = 2,171 ms」は plain node の測定であり、
`utilityProcess` では同じ作業が 2,506〜4,193 ms になる。
[AD-028](../../docs/decisions/0028-session-enumeration-process-and-unc-handoff.md) §1 が
「要求 1 回の短命プロセス」を選んだ判断の前提に、この差は入っていなかった。

### 人間判断 (2026-09-18)

**予算は変えない。実装を予算に合わせる。**
選択されたのは「**常駐 1 プロセスで直列**」であり、
[AD-030](../../docs/decisions/0030-enumeration-runs-in-one-resident-process.md) として起票した。

判断の材料になった追加の実測:

| 測定 | 結果 |
| --- | --- |
| `utilityProcess` の**起動だけ** (SDK を読まない) | 2,704〜2,839 ms |
| `ELECTRON_RUN_AS_NODE` での**起動だけ** | 2,784〜2,938 ms |
| 素の `node` での**起動だけ** | 909〜959 ms |
| 親の env を全部渡した場合の起動 | 2,618 ms (**許可リストは原因ではない**) |
| **1 プロセスで直列に 2 所在 × 2 巡** | **合計 1,083 ms** (import 165 / ホスト 82・40 / WSL 512・280) |

**1 プロセスで env を書き換えながら直列に読める**ことを確かめた —
ホストの 2 回が一致し、WSL の 2 回が一致し、2 つの識別子集合は交わらなかった。
SDK は config ディレクトリの**値をキーに**メモ化するため、
env を書き換えれば正しく別の結果が返る。

**AD-021 §3 の却下は撤回していない。** 「並行に列挙する限り危険」という前提を
明示したうえで、**直列という条件つき**で読み替えた (AD-030 §3)。

### AD-030 実装後の 1 回目 (2026-09-18) — **失敗**

先頭ページ **31,420 ms**。要求が 1 件も返らず、全部が上限時間に当たっていた
(`list-sessions-enumerate` 30,032 ms = 15,000 ms × 2 件)。

原因は **2 つあり、どちらも単体テストでは出ない形**だった。

1. **応答の経路が噛み合っていなかった。** 子は**要求を受け取った経路で返す**ため
   `parentPort` に応答を載せていたのに、親は**標準出力だけ**を購読していた。
   要求は届いており、応答だけが捨てられていた。
   親のテストは `EnumerationWorkerLauncher` を差し替えて書くので、
   **実際の経路が 2 本あること自体がテストの外にある**。
2. **上限時間の定数が 2 箇所にあった。** AD-030 で 10 秒に詰めたつもりが、
   実際に効いていたのは呼び出し側の 15 秒だった。
   同じ名前で別の値が並んでおり、型でも lint でも衝突しない。

修正後、**Electron から常駐プロセスへ要求を直接投げて**測った
(暖機 3 秒を置き、アプリ起動時に済む分を除いてある)。

| 要求 | 結果 |
| --- | --- |
| ホスト 先頭 50 件 | **127 ms** |
| `Ubuntu-26.04` 先頭 50 件 | 1,594 ms |
| `Ubuntu-22.04` 先頭 50 件 | 1,333 ms |
| ホスト 全件 (55 件) | 170 ms |
| `Ubuntu-26.04` 全件 (**277 件**) | 6,954 ms |

| 2 巡目 ホスト 先頭 50 件 | 839 ms |
| 2 巡目 `Ubuntu-26.04` 先頭 50 件 | 1,715 ms |

**起動費用 2,704 ms は消えた。** AD-030 の目的は達している。
残るのは **UNC の I/O** であり、ホストの 127 ms に対して WSL は 1.3〜1.6 秒かかる。

**副産物: 存在しない config ディレクトリは失敗にならない。**
綴りを間違えた UNC パスを渡すと、**11,914 ms 待ってから `ok` / 0 件**が返った。

**上限時間がこの形の最後の砦である**ことを意味する (contracts C-5)。

### 人間判断 (2026-09-18) — 描画の開始点と計測の単位

上の [RISK] が予告していた「予算ではなく**描画の開始点**を見直す」を実行した。

| 決定 | 内容 |
| --- | --- |
| **所在ごとの段階描画** | 探索のあと、所在 1 件の先頭ページが届くたびに画面へ流す。途中は `complete: false` のままで件数を確定値として見せない (FR-037) |
| **SC-008 の計測単位を文面に合わせる** | `list-sessions-first-rows` (先頭 50 件が出そろうまで。2,000 ms) と `list-sessions-all-location` (**1 所在あたり**。10,000 ms) を置き、**全所在の合計**である `list-sessions-first-page` / `list-sessions-all` からは予算を外した |

**合計に予算を置いていたのは誤りだった。** SC-008 は「**1 所在あたり** 700 件規模」と
書いており、合計に置くと**所在が増えるだけで SC-008 が求めていない超過を報告する**。

### AD-030 実装後の 4 回目 (2026-09-18) — **SC-008 の判定**

| 計測点 | 実測 | 予算 | 判定 |
| --- | --- | --- | --- |
| **`list-sessions-first-rows`** | **1,841 ms** | 2,000 ms | **ok** |
| **`list-sessions-all-location`** (4 所在) | 81 / **7,282** / 1,846 / 0 ms | 10,000 ms | **すべて ok** |
| `list-sessions-cached` | **0 ms** | 100 ms | **ok** |
| `list-sessions-verify` (内訳) | 1,185 ms → 2 巡目 **0 ms** | — | |
| `list-sessions-discover` (内訳) | 1,197 ms → 2 巡目 **6 ms** | — | |
| `list-sessions-first-page` (合計の内訳) | 4,856 ms | — | 全所在ぶんが揃うまで |
| `list-sessions-all` (合計の内訳) | 9,216 ms | — | |

**実測値はすべて予算内である。** ただし **[RISK] が 2 件残る。**

**[RISK-1] 先頭 50 件の余裕は 159 ms しかない。**
内訳の 1,197 ms は探索であり、そのうち **1,185 ms は `wsl.exe` の実行状態確認**である。
**予算の 59% を列挙以前の固定費が食っている。**
次の手は決まっている — **実行状態の確認をアプリ起動時に済ませる**。
そうすれば先頭 50 件は約 650 ms になる。
今回採らなかったのは、変更点を 1 つに絞って効果を切り分けるためである。

**[RISK-2] 700 件規模では予算を満たさない見込みである。**
SC-008 は「1 所在あたり **700 件規模**の全件取得完了が 10 秒以内」と書いているが、
**この開発ホストの最大所在は 277 件であり、700 件の所在が存在しない。**
外挿は予算を超える。

| 所在 | 件数 | 実測 | 1 件あたり |
| --- | --- | --- | --- |
| ホスト既定 | 55 | 81 ms | — |
| `Ubuntu-26.04` (UNC) | **277** | **7,282 ms** | — |
| `Ubuntu-22.04` (UNC) | 81 | 1,846 ms | — |
| 同一所在の 50 件 / 277 件の差 | 227 件差 | 1,594 → 6,954 ms | **約 23.6 ms** |

外挿すると **700 件で約 17 秒**であり、**予算の 10 秒を超える**。
**「実測が予算内」と「SC-008 を満たす」は同じではない** — 700 件の所在で測れていない。

**この残余を予算の読み替えで消してはならない。** 予算は人間が承認した値である。
取りうる手は 2 つあり、どちらも R-2 の範囲外である。

1. **700 件規模の所在を作って測る** (`.claude/projects` に合成の履歴を置く)。
   測っていないものを満たしていると書かないために、まずこれが要る
2. UNC の 1 件あたり 23.6 ms を下げる。全件取得を**所在ごとの段階描画の中に隠す**形は
   既に入っているため、利用者が待つのは先頭 50 件だけである。
   全件の所要は「完了の通知が遅れる」という形で現れる

### [RISK-1] の決着 (2026-09-18 の人間判断)

**2 回目で余裕が 21 ms まで詰まった** (内訳の `list-sessions-verify` が 1,373 ms)。
2 回の実測で余裕は 159 ms と 21 ms であり、**`wsl.exe` の固定費のばらつきに飲まれる幅**である。
手当てを入れることが選択された。**入れたのは 2 つで、効いたのは後者である。**

| 手当て | 内容 | 効果 |
| --- | --- | --- |
| 起動時の暖機 | `sessions.warmUp()` が実行状態の確認を先に済ませる | **限定的**。有効期間は 30 秒であり、起動から時間が経って開けば払い直す |
| **所在 `windows` を先出し** | ホストは**実行中確認を待たずに**列挙して描く。ホストに確認は要らない | **これが効いた** |

**3 回目のログが順序で証明している。**

```
[measure] list-sessions-first-rows 1248ms / 予算 2000ms (ok)
[measure] list-sessions-verify 1346ms
[measure] list-sessions-discover 1367ms
```

**先頭 50 件 (1,248 ms) が実行中確認 (1,346 ms) より先に出ている。**
暖機の値は期限切れだったため固定費は払われているが、
**もう先頭ページの予算には乗っていない**。余裕は 21 ms から **752 ms** になった。

**固定費を消したのではない。払う場所を変えた** — 確認は FR-008 の門として構造的に要る。
ホストの履歴が 50 件に届かない機体では次の所在へ落ち、そのときは固定費を払う
(確認を経ずに UNC を触れない)。**この機体はホストが 56 件あるため効いている。**

構造は `session-service.test.ts` の
「所在 `windows` は実行中確認を待たずに描く」と
「`warmUp()` が実行中確認を先に済ませ、一覧で払い直さない」が固定している。

| 確認 | 結果 |
| --- | --- |
| 先頭ページ表示中にグループ件数を確定値として見せていない | **成立** (段階描画中は `complete: false` のまま。`session-service.test.ts` 「所在ごとに段階的に通知する」が構造を固定) |
