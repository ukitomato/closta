## R-01: 列挙は `CLAUDE_CONFIG_DIR` を与えた SDK 呼び出しで行う。UNC 経路で成立する

**問い**: WSL ディストロ内の config ディレクトリを Windows 側から列挙できるか。
[AD-021](../../docs/decisions/0021-session-store-and-enumeration.md) は
「`listSessions()` は config ディレクトリを引数で取れない。Provider ごとの短命 child process が本線」
とだけ決めており、**その child process をどこで動かすか**は未決だった。
ディストロ内で動かすなら Node と SDK の導入が要り、Principle VI に反する。

**測定**: `CLAUDE_CONFIG_DIR` を UNC 経路に設定した Windows 側の Node プロセスから
`listSessions()` を呼んだ。

| 対象 config ディレクトリ | 件数 | 全件 | 先頭 50 件 | programmatic 除外 |
| --- | --- | --- | --- | --- |
| `//wsl.localhost/Ubuntu-26.04/home/<user>/.claude` | 269 | 915 ms | 384 ms | 229 件 / 892 ms |
| `\\wsl.localhost\Ubuntu-26.04\home\<user>\.claude` | 269 | 984 ms | 391 ms | 229 件 / 973 ms |
| `\\wsl$\Ubuntu-26.04\home\<user>\.claude` | 269 | 936 ms | 419 ms | 229 件 / 929 ms |
| `C:\Users\<user>\.claude` (ホスト既定) | 43 | 44 ms | 45 ms | 35 件 / 39 ms |

**決定**: **Windows 側のプロセスで、`CLAUDE_CONFIG_DIR` に UNC 経路を与えて SDK を呼ぶ。**

- ディストロ内で何も動かさないため、Node / SDK の導入が不要になる (Principle VI / FR-013)
- `wsl.exe` を 1 度も呼ばない (FR-006 / SC-003)
- JSONL の自前パースをしない (Principle IV / FR-001)
- 3 つの UNC 表記はいずれも成立する。**新しい `\\wsl.localhost\` を使う** (AD-015 §1)

**根拠として確認した SDK 側の実装事実**: `listSessions()` に `sessionStore` を渡さない経路は
`fs/promises` の `readdir` / `stat` / `open` でローカルファイルシステムを読むだけであり、
`claude` 実行ファイルを起動しない。config ディレクトリは `process.env.CLAUDE_CONFIG_DIR`
から解決され、**その値をキーにメモ化**されている (同一プロセス内で値を変えれば別の結果になるが、
非同期処理の途中で読み直される箇所があるため R-04 の判断は変わらない)。

**採らなかった案**:

| 案 | 却下理由 |
| --- | --- |
| `wsl.exe -d <D> -- node <script>` でディストロ内の SDK を呼ぶ | ディストロへの Node / SDK 導入が要る (Principle VI 違反)。加えて呼び出しあたり約 1.5 秒 (AD-015) |
| `listSessions({ dir })` で登録フォルダごとに絞る | `dir` は Windows 側で `path.resolve` を通るため、POSIX 形式の値が `C:\home\...` に解決されて transcript ディレクトリ名が一致しない。**全件列挙して突き合わせる**ほうが構造的に安全であり、実測でも十分速い |
| JSONL を直接読む | Principle IV 違反 |

## R-02: 作業ディレクトリの名前空間は「値の形」から判定する

**問い**: セッションの作業ディレクトリは、由来 config ディレクトリの所在の名前空間で
書かれていると仮定できるか。

**測定**: 作業ディレクトリの形を分類した。

| 由来 config ディレクトリ | Windows 形式 | POSIX 形式 | UNC 形式 | 不在 |
| --- | --- | --- | --- | --- |
| ホスト既定 (43 件) | 30 | 6 | **7** | 0 |
| `wsl:Ubuntu-26.04` (269 件) | 0 | 268 | 0 | **1** |

**ホスト側の 1 つの config ディレクトリに 3 形式が同時に現れた。**
`\\wsl.localhost\Ubuntu-26.04\home\<user>\ags\ags-platform` のように
**UNC 形式で記録されたもの**が 7 件あり、POSIX 形式 (`/home/<user>/ags/ags-platform`) も 6 件ある。
小文字のドライブレター (`c:\dev\...`) も混ざっていた。

**決定**: **由来 config ディレクトリの所在から名前空間を推定しない。値の形から判定する** (FR-016)。
判定は 5 つの出自に落とす。

| 出自 | 判定条件 | 所在 |
| --- | --- | --- |
| `host` | ドライブレター始まり | `windows` |
| `wsl-from-unc` | UNC 形式 | **UNC に埋め込まれたディストロ名**で特定 (FR-017) |
| `wsl-inherited` | POSIX 形式 かつ 由来 config の所在が `wsl:<D>` | `wsl:<D>` (FR-018) |
| `unknown-location` | POSIX 形式 かつ 由来 config の所在が `windows` | **特定しない** (FR-018) |
| `absent` | 値が無い | — (FR-028) |

`unknown-location` を推測で埋めないのは、**同じ `/home/y/p` が複数のディストロに存在しうる**
ためである ([AD-025](../../docs/decisions/0025-workspace-folder-carries-location.md) の
「作業フォルダを『パス』として登録すると所在が失われる」と同じ理由)。
1 つのディストロに帰属させると、別のディストロの登録フォルダにセッションが紛れ込む。

**`wsl-from-unc` は R-1 の `fromUnc()` で変換できる。** UNC 値はディストロ名を含むため、
所在を推測せずに特定できる。ディストロが検出済み集合に無い場合は「未検出の所在」とする (FR-017)。

## R-03: config ディレクトリの探索は UNC の浅い列挙で足りる

**問い**: ディストロ内のどこに config ディレクトリがあるかを、ディストロ内でコマンドを
実行せずに知れるか。R-1 は**ディストロの既定ユーザ名を保持していない**。

**測定**:

| 操作 | 所要 | 結果 |
| --- | --- | --- |
| `\\wsl.localhost\Ubuntu-26.04\home` のディレクトリ列挙 | **69 ms** | `linuxbrew` / `yukiyamato` |
| `home/<user>/.claude` の存在確認 | 即時 | `yukiyamato` にあり / `linuxbrew` に**なし** |
| `root/.claude` の存在確認 | 即時 | **Access denied** (権限拒否) |
| `home/<user>/.claude/projects` のディレクトリ列挙 | 57 ms | 19 プロジェクト |
| 同 配下の `*.jsonl` 再帰列挙 | 2,110 ms | 844 ファイル |

**決定**: **ホーム配下の浅い列挙で候補を集め、`.claude` の存在する候補すべてを対象にする**
(FR-010 / FR-011)。`/root` も候補に含めるが、権限拒否は**その候補の失敗**として扱い、
所在全体の失敗にしない (FR-030 / FR-031)。

再帰列挙 (2,110 ms) は**行わない**。必要なのは config ディレクトリの所在確認までであり、
配下の走査は SDK に任せる (R-01 で全件 915 ms)。**自前で再帰列挙すると SDK より遅く、
しかも Principle IV に触れる**。

**`wslpath` / `wsl.exe` は使わない。** 1 回あたり約 1.5 秒かかり (AD-015)、
候補ごとに呼ぶと探索だけで数秒を失う。

## R-04: 実行単位は「対象 config ディレクトリごとの短命 `utilityProcess`」

**問い**: FR-005 (main をブロックしない) / FR-014 (環境変数の書き換えで切り替えない) /
FR-045 (Electron とネイティブに非依存) を同時に満たす実行単位は何か。

**制約の重なり**:

- SDK は `CLAUDE_CONFIG_DIR` を**プロセス単位の環境変数**として読む (R-01)
- 同一プロセス内で環境変数を書き換える方式は AD-021 §3 が却下している (並行列挙のレース)
- 列挙は 1 所在あたり最大 1 秒近くかかり、main process で回すと UI が止まる (Principle IX)
- Agent SDK を呼ぶコードは `agents` レイヤに属する ([AD-023](../../docs/decisions/0023-application-architecture.md) §2)
- `agents` は Electron API とネイティブモジュールに依存できない (AD-010 / Principle VII)

**測定**: 冷えた状態の子 Node プロセスで `import` + `listSessions()` を 1 回通して **2,171 ms**
(内訳: プロセス起動 + SDK の `import` に約 300 ms、列挙に約 900 ms、計測の外殻を含む)。

**決定**: **対象 config ディレクトリごとに 1 つの短命 `utilityProcess` を起動して列挙し、
結果を構造化データで返して終了させる。**

- AD-021 §3 の「Provider ごとの短命 child process」をそのまま本プロジェクトのレイヤに載せた形
- 環境変数はプロセス生成時に与えるため、書き換えが起きない (FR-014)
- 所在ごとに独立しているため、1 つの失敗が他に波及しない (FR-030)
- `agents` レイヤに置けるため AD-010 / Principle VII と整合する (FR-045)
- 列挙中の I/O とパースが main の外に出る (FR-005)

**先頭ページの体感を保つため、要求は 2 段に分ける** (R-06)。

**`agents` をセッションごと 1 プロセスとする AD-023 §6 との関係**: 本 feature の列挙プロセスは
セッションに紐づかない **3 つ目の寿命**を持つ (アプリ起動〜終了が `infra`、
セッション開始〜終了が `agents`、**要求 1 回が列挙プロセス**)。
AD-023 §6 の理由 (1 プロセスで全セッションを捌くと 5MB のパースが他を止める) は
列挙にも当てはまるため、**要求ごとに分ける方針は同じ**である。
この寿命の追加を ADR に記録する。

## R-05: UNC 形式の config ディレクトリを列挙プロセスへ渡す扱い

**問い**: AD-025 は「**UNC 形式は `infra` の内側に閉じる**」と定めている。
列挙プロセス (`agents`) に UNC 形式の config ディレクトリを渡すことは、この規則に反しないか。

**評価**: 字義どおりには反する。しかし代替はいずれも悪い。

| 案 | 評価 |
| --- | --- |
| 所在 + ランタイム名前空間のパスを渡し、**列挙プロセス側で UNC を組み立てる** | UNC の組み立てが `agents` に入る。`infra` の内側に閉じるという規則の**意図に最も反する** |
| 列挙を `infra` (main process) で行う | FR-005 (main をブロックしない) を満たせない |
| 列挙プロセスを `infra` のサブディレクトリに置く | Agent SDK を呼ぶコードは `agents` という AD-023 §2 に反する。レイヤ規則が二重になる |

**決定**: **UNC 形式の組み立ては `infra` に限り、組み立て済みの値を
「その 1 プロセスの起動引数」としてのみ渡す。** 次の 4 点を規則として固定し、ADR に記録する。

**訂正 (design-gate round 1)**: 初版は規則 1 を「`infra` の **1 箇所**に限る」と書いたが、
**HEAD で既に成立していない**。UNC 値を文字列として materialize している production コードは
`src/main/infra/fs/wsl-fs.ts` の `toUncValue()` が既に 1 件あり、本 feature の
`config-dir.ts` は 2 件目になる。組み立て (branding) 自体は `src/domain/runtime/path-api.ts`
の `toUnc()` にあり `domain` である。**「1 箇所」という表現は書いた時点で事実と違った。**
`services-not-to-io` と同じ**実名リスト方式**に改める。

1. **UNC 値を文字列として materialize してよいモジュールを実名で列挙する**
   (`src/main/infra/fs/wsl-fs.ts` / `src/main/infra/session/config-dir.ts`)。
   **branding はパス API に限る**
2. 列挙プロセスは受け取った値を**そのまま SDK に渡すだけ**とし、結合・分解・正規化をしない
3. 列挙プロセスは**パス値に一切触らない**。作業ディレクトリは生の文字列のまま返し、
   出自の判定と名前空間つきの値への変換は `domain` の純粋関数が行う
   (**訂正**: 初版は「所在の名前空間に変換して返す」と書いていたが、
   変換に要する `parseWslUncPath()` は `src/agents/` で禁止されている。
   AD-028 §3 の訂正 / AD-029)
4. UNC 形式を IPC 境界と永続化境界に出さない (FR-042 / AD-025 の元の規則そのまま)

これにより「UNC が現れる範囲」は **`infra` の実名 2 モジュール**と、
`agents` の**受け渡しだけを行う 1 行**に限定される。

**規則 1 / 2 には機械検証を付ける** (design-gate round 1 の指摘)。
規則が「書いてある」だけでは AD-027 §1 の「ルールは違反サンプルで発火したことで確認する」を
満たさない。規則 1 は `check.mjs` の許可モジュール照合、規則 2 は
`src/agents/` 内に UNC 接頭辞リテラルと `toUnc` 呼び出しが 0 件であることで見る。

## R-06: 要求は「先頭ページ」と「全件」の 2 段に分ける

**測定** (R-01 の表より): 269 件の config ディレクトリで、先頭 50 件 **384 ms** / 全件 **915 ms**。
プロセス起動と `import` に約 300 ms。

**決定**: 一覧を開いたときは**先頭ページ**を要求し、描画後に**全件**を要求する (FR-037 / FR-038)。

- 先頭ページ: 約 300 + 384 = **約 700 ms** → SC-008 の「先頭 50 件 2 秒以内」に収まる
- 全件: 700 件規模でも線形なら約 2.5 秒 → SC-008 の「10 秒以内」に収まる
- グループ分け (登録フォルダ / 未登録 / 保留 / 不明) は**全件が揃ってから確定する**。
  先頭ページの段階では「取得中」を示す

**`limit` を指定しても所要が 0 にならない**点に注意する。SDK は全プロジェクトディレクトリを
走査してから並べ替えるため、先頭ページでも走査は一巡する。
**ページングは転送量と本文読み取りを減らすもので、走査を減らすものではない。**

## R-07: 読み取り専用であることは前後比較で測る

**測定**: 列挙の前後で対象 config ディレクトリ配下の全ファイル
(**8,487 件**) の名前・サイズ・更新時刻を比較し、**差分 0 件**を確認した。

**決定**: SC-004 の計測経路をこの前後比較とする。加えて、書き込み系 SDK API
(`renameSession` / `tagSession` / `deleteSession` / `importSessionToStore` / `query`) の
**呼び出し形**を検証スクリプトで走査する (R-1 の Principle 検証と同じ方式)。

**名前の出現ではなく呼び出し形で判定する。** import しただけの名前や型注釈を違反にすると、
`session` domain が将来これらを使う feature (X-1 / O-1) で検証が破綻する。

## R-08: 停止中ディストロは「UNC 経路を発行しない」ことで守る

**問い**: 停止中のディストロに対する `\\wsl.localhost\<D>\...` へのアクセスは、
ディストロを起動してしまうか。

**この問いは実測しない。** 測定それ自体が停止中ディストロを起動する可能性があり、
検証のために開発ホストの状態を変える行為になる。

**決定**: **起動するかどうかに依存しない設計にする。** R-1 の
「実行中確認済みの値に対してのみファイルアクセスを発行する」契約を列挙にも適用する (FR-008)。

- 所在が停止中なら、**config ディレクトリの探索も列挙プロセスの起動も発行しない**
- 停止中の所在の識別子で列挙を直接要求されても、**実行状態を取り直してから拒否する**
  (R-1 の `probeRuntime` と同じ形)
- 「未列挙」の理由を返し、起動と再検出の導線を添える (FR-007 / FR-031)

**残余**: 実行状態の確認から UNC 経路の発行までの窓は消せない。
R-1 の SC-005 と同じく、**SC-002 はアプリ側の発行行為で測る**。

## R-09: worktree 由来と programmatic 由来は取得して区別する

**測定**: 269 件のうち `includeProgrammatic: false` で落ちるものが **40 件** (約 15%)。
worktree の作業ディレクトリは登録フォルダ配下の `.claude/worktrees/<name>` に現れた
(例: `/home/<user>/sandbox/kanata/.claude/worktrees/010-...`)。

**決定**: SDK の既定 (いずれも含む) で取得し、**区別して保持する** (FR-029)。

- 落とすと、SDK 経由で動かしたセッション (Closta 自身が将来起動するものを含む) が消える
- worktree の作業ディレクトリは**最長一致で親の登録フォルダに対応づく** (FR-024)。
  worktree であることは別の属性として保持し、一覧で区別できるようにする

## R-10: キャッシュはプロセス寿命とし、再取得は明示操作に限る

**決定**: R-1 の検出キャッシュと同じ方針を採る (FR-033 / FR-035 / FR-036)。

- キャッシュはアプリプロセスの寿命。ディスクに書かない (FR-036 / SC-014)
- 自動ポーリングとファイル監視をしない。**正本がアプリ外にある以上、鮮度は原理的に保証できない**
  ので、**取得時刻を見せて判断を利用者に残す** (FR-034)
- 再取得はキャッシュを**置き換える**。マージすると、アプリ外で削除されたセッションが残る

`fs.watch` を UNC 経路に対して張る案は採らない。**AD-015 が UNC を「読み取りは速い」と
評価した根拠は単発アクセスの実測であり、監視の負荷は測っていない。**
測っていないものに常時動作を賭けない。

## 本 feature で意図的に扱わない調査項目

| 項目 | 先送り先 | 理由 |
| --- | --- | --- |
| `SessionStoreEntry` の型と SQLite スキーマ | I-1 (SPIKE-11) | 本 feature は永続化しない |
| `sessionStore` を渡した列挙経路 | I-1 | `@alpha` であり、コンテナ内セッションが出てから必要になる |
| `getSessionMessages()` の所要と本文の運び方 | R-3 | 本 feature は一覧とメタデータまで (`[USER]` 確定) |
| 複数 Provider の config ディレクトリ | X-3 | 所在ごとの既定のみ (`[USER]` 確定) |
| 停止中ディストロへの UNC アクセスの副作用 | — | R-08。測定自体が状態を変えるため行わない |
| `wsl.exe` の 1.5 秒が他ホストでも同じか | — | AD-015 の Open Question のまま。本 feature は `wsl.exe` を使わないため影響しない |
