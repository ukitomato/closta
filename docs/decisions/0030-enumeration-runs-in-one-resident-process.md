# AD-030: セッション列挙を「常駐 1 プロセス + 直列処理」に変える

## Context

[AD-028](0028-session-enumeration-process-and-unc-handoff.md) §1 は列挙の実行単位を
**「列挙対象ごと・要求 1 回の短命 `utilityProcess`」**と決めた。
その判断の根拠は [research R-01](../../specs/002-session-cross-folder-session-enumeration/research.md) の
「冷えた子プロセスで import + 1 回の列挙 = 2,171 ms」である。

**この値は素の `node` の測定だった。** 実機 (Electron) で測り直したところ、
先頭ページの取得が **12,331 ms** かかり、SC-008 の予算 2,000 ms を 6 倍超過した。

内訳を計ると、**費用のほぼ全部がプロセスの起動**であり、列挙そのものは 100 ms 未満だった。
つまり「要求 1 回の短命プロセス」という形そのものが予算の下限になっていた。

## 実測 (2026-09-18 / 実機)

開発ホスト 1 台。`out/main/enumerate-sessions-*.js` を各手段で起こし、
親が `fork` した時刻から**最初の応答が届くまで**を測った。

### プロセスの起動と列挙の比

| 測定 | 結果 |
| --- | --- |
| `utilityProcess` の**起動だけ** (SDK を読まない) | **2,704〜2,839 ms** |
| `ELECTRON_RUN_AS_NODE` での**起動だけ** | 2,784〜2,938 ms |
| 素の `node` での**起動だけ** | 909〜959 ms |
| SDK の import | 165〜261 ms |
| **ホストの列挙 10 件** | **36 ms** |
| **ホストの列挙 50 件** | **65〜83 ms** |
| 2 回列挙 (`programmatic` の差集合) の追加分 | 26〜53 ms |
| WSL の列挙 50 件 (UNC 経路) | 512〜944 ms |

**件数は効かない。** 10 件と 50 件の差は 35 ms である。
**起動手段も効かない。** `utilityProcess` と `ELECTRON_RUN_AS_NODE` は同値であり、
遅いのは `electron.exe` の起動そのものである (素の `node` の 3 倍)。
**環境変数の許可リストも効かない。** 親の環境を全部渡しても 2,618 ms だった。

### 並行に起こすと遅くなる

| 測定 | 結果 |
| --- | --- |
| WSL の子を 1 件だけ | 4,193 ms / 2 回目 4,104 ms |
| ホスト + WSL を**同時**に 2 件 | ホスト 2,880 ms / WSL **10,470 ms** |
| 3 件を**同時** | 2,952 / 10,022 / **11,419 ms** |

[contracts C-6](../../specs/002-session-cross-folder-session-enumeration/contracts/session-enumeration.md)
は「異なる列挙対象は並行して実行してよい」と許しているが、
**実測では許すだけで得にならない。** utility process の起動が資源を食い合う。

### 1 プロセスで直列に読めるか

**読める。** 1 プロセスで `process.env.CLAUDE_CONFIG_DIR` を各呼び出しの直前に設定し、
**直列に** 2 つの config ディレクトリを 2 巡した。

| 操作 | 結果 |
| --- | --- |
| SDK の import | 165 ms |
| ホストの先頭 50 件 | 82 ms |
| WSL の先頭 50 件 | 512 ms |
| ホスト 2 回目 | 40 ms |
| WSL 2 回目 | 280 ms |
| **合計** | **1,083 ms** |

**結果は正しく分かれた** — ホストの 2 回が一致し、WSL の 2 回が一致し、
2 つの識別子集合は交わらなかった。SDK は config ディレクトリの**値をキーに**メモ化するため、
env を書き換えれば別の結果が返る (research R-01 が確認した実装事実と整合する)。

## Decision

### 1. 列挙の実行単位を「常駐 1 プロセス + 直列処理」にする

`src/agents/` に置く子プロセスを **1 つだけ常駐させ**、
すべての config ディレクトリを**直列に**処理する。

| 制約 | どう満たすか |
| --- | --- |
| main process をブロックしない (Principle IX) | 別プロセスのまま |
| `electron` とネイティブに依存しない (AD-010 / Principle VII) | 子の実装は変わらない。stdin から要求を読む形でも単独起動できる |
| Agent SDK を呼ぶコードは `agents` (AD-023 §2) | 変わらない |
| ディストロ内に何も導入しない (Principle VI) | 変わらない |
| 環境変数のレース (AD-021 §3) | **同時に 1 要求しか扱わない**ことで構造的に消す (下記 §3) |

### 2. config ディレクトリは要求ごとに渡す

起動時の環境変数ではなく、**要求 1 件ごとに値を渡す**。
子は SDK を呼ぶ直前に `process.env.CLAUDE_CONFIG_DIR` へ設定する。

**AD-028 §3 の規則 2 は変わらない** — 子は受け取った値を**そのまま**渡すだけであり、
結合・分解・正規化をしない。UNC の文字列リテラルも UNC API 呼び出しも持たない
(検証項目 12 / 13 はそのまま効く)。

**`CLAUDE_CONFIG_DIR` の綴りを持つモジュールは `src/agents/enumerate-sessions.ts` の 1 つだけになる。**
起動時の環境変数から外れるため、`infra` 側はこの綴りを持たなくなる —
許可リストが 2 箇所から 1 箇所に減る。

**環境変数の許可リスト (FR-050 / SC-016) は残る。** 常駐プロセスにも
親環境を継承させない。config ディレクトリが env から外れた分だけ、
渡す値は Windows で Node の起動に要る最小集合だけになる。

### 3. AD-021 §3 の「環境変数の書き換えの却下」を**直列という条件つきで読み替える**

AD-021 §3 は「同一プロセス内で環境変数を書き換える」案を
**並行列挙のレース**を理由に却下した。その懸念は正しい。

本 ADR は却下を**撤回しない**。**前提を限定する。**

- **並行に列挙する限り、環境変数の書き換えは危険である** — この判断は維持する
- **同時に 1 要求しか扱わなければレースは起きない。** 要求は待ち行列に入り、
  1 件ずつ処理される。env を設定してから応答を返すまでのあいだ、
  その値を変える主体が存在しない
- **並行に列挙する動機も消えた** — 実測で並行のほうが遅い (上記)

**AD-021 を in-place 改変しない。** 読み替えの根拠を本 ADR に置く —
[AD-025](0025-workspace-folder-carries-location.md) §2 が [AD-004](0004-branded-path-types.md) に対して、
AD-028 §2 が [AD-023](0023-application-architecture.md) に対して確立した形式に従う。

### 4. AD-028 §1 と contracts C-1 の「要求 1 回の寿命」を読み替える

AD-028 §1 は `agents` に 3 つ目の寿命「要求 1 回」を追加した。
本 ADR はこれを **「アプリのプロセス寿命」**に差し替える。

**AD-028 §1 が挙げた 5 つの制約は、常駐でもすべて満たされる** (上記 §1 の表)。
崩れたのは制約ではなく**費用の前提**である。

**contracts C-1 の「列挙対象 1 件につき 1 プロセスを起動し、結果を返して終了する」**は
「**1 プロセスが要求を直列に処理する**」に置き換わる。
「失敗しても他の列挙対象に波及させない」(FR-030) は
**プロセスの分離ではなく要求ごとの失敗の封じ込め**で満たす —
1 要求の失敗は理由キーになり、待ち行列の次の要求は影響を受けない。

### 5. 要求の経路は `parentPort` の薄い adapter を通す

**`utilityProcess` は標準入力を支えていない。**
`ForkOptions.stdio` の説明に「`stdin` を `ignore` 以外に設定するのは非対応であり
エラーになる」と明記されており、`UtilityProcess` に `stdin` のメンバも無い。
常駐させて要求を送るには別の経路が要る。

**採る形**: [AD-028](0028-session-enumeration-process-and-unc-handoff.md) の Consequences が
前もって許していたもの —

> `process.parentPort` は import を伴わないため ESLint にも依存グラフにも現れない —
> **機械検証が緑でも守れていない形になりうる**ので、Electron 抜きの `node` で
> 1 件の列挙が成立することをテストで確かめる

- **本体は「行を読み、行を書く」だけ**にする。経路を知らない
- **経路の選択は `src/agents/transport.ts` の 1 モジュールに閉じる**。
  `process.parentPort` があればそれを使い、無ければ標準入出力を使う
- **単独起動の形は標準入出力側で保たれる** (Principle VII / SH-094)。
  `node <entry>` に要求の行を流せば応答が返る

**訂正 (2026-09-18)**: 上の 3 点だけでは足りなかった。
**子は「要求を受け取った経路」で返す**ため、Electron 下では応答も `parentPort` に載る。
親が標準出力だけを購読していたので、**要求は届いて応答だけが捨てられ**、
実機で全要求が上限時間に当たった (先頭ページ 31,420 ms)。

**親は 2 つの経路の両方を購読する。** 経路を 1 つに決めるのは子の側 (`transport.ts`) であり、
親がそれを先読みして片方だけを見ると、選択が変わった瞬間に無言で壊れる。
どちらで返ってきても同じ 1 行として扱う。

**この形は単体テストの外にある。** 親のテストは `EnumerationWorkerLauncher` を
差し替えて書くので (BE-025c)、**実際の経路が 2 本あること自体がテストに現れない**。
`node` 単独起動の確認 (SH-094) も標準入出力側しか通らないため緑になる。
**Electron を立てた実機の確認でしか出ない。**

**採らなかった案**: `child_process` で `ELECTRON_RUN_AS_NODE` を使う。
標準入出力が完全に使えるので本体は経路を 1 つだけ持てばよくなるが、
**プロセス起動は `src/main/infra/runtime/` のみ**という規則 (FR-036 / `MSG_SPAWN`) に触れる。
起動層を `infra/runtime/` へ移すと `@agents/...?modulePath` を import できない
(`infra → agents` は AD-023 §7 が禁じている)。
**規則を曲げるより、ADR が前もって許した形を使う。**

### 6. アプリの起動時に先に起こす

起動費用 (約 2.7 秒) を**アプリ起動時に払う**。
R-1 のランタイム検出が既に約 4 秒かかっているため、その裏に隠れる。

**一覧を開く操作の費用は列挙だけになる** (実測で 2 所在 600 ms 程度)。
これで SC-008 の先頭ページ 2 秒を余裕を持って満たす。

**起動に失敗しても一覧を開けなくしない。** 常駐プロセスが無ければ
最初の要求の時点で起こす (遅いが動く)。

### 7. 落ちたら作り直す

常駐プロセスは落ちうる。**落ちたことを検知して作り直す**。

- 実行中だった要求は**その要求の失敗**として返す (`enumeration-failed`)
- 待ち行列に残っている要求は、作り直した後のプロセスで処理する
- **無限に作り直さない。** 連続した失敗に上限を設け、超えたら
  「列挙できない」状態として理由を返す — 落ち続けるプロセスを起こし続けない

## Consequences

- **SC-008 の予算を変えない。** 予算は人間が承認した値であり、
  実装が届かないことを理由に読み替えるものではない。**実装を予算に合わせる**
- **同時プロセス数の上限 (C-6) は意味を失う。** プロセスは 1 つである。
  代わりに**待ち行列の長さ**と**逐次の連打のクールダウン**が上限の役割を持つ
- **`programmatic` の 2 回列挙の費用は無視できる** (26〜53 ms)。
  design-gate L-002 の対応をそのまま維持してよい
- **`before-quit` で常駐プロセスを終了させる** (AD-028 と同じ)。
  UNC ハンドルを掴んだ孤児を残さない
- **メモリは 1 プロセス分**。対象ごとに常駐させる案 (検討したが採らなかった) は
  対象数ぶんのメモリを使う
- **単独起動の形は保つ** (Principle VII / AD-010)。
  stdin から要求を読む形でも `node <entry>` で動き、標準入出力でプロトコルを話す。
  **この確認を再度行う** — SH-094 の形が変わるため
- **実機での計測を受け入れ条件に含める。** 今回のバグ 2 件
  (子が終了しない / 先頭ページを 2 回取る) と本 ADR の発端は、
  いずれも**ユニットテストと単独起動確認では出なかった**。
  「素の `node` で速いこと」は「実機で速いこと」を意味しない
